## 004 · 助手 · 2026-10-18T13:39:45.078Z

**这道题值得认真做：题面不大，但很能区分“会调用模型”和“能把 Agent 做稳定”。** 我的判断是，拉开差距的地方会是会话隔离、工具执行一致性、压缩后的连续性，以及能否用测试证明这些行为。

“两小时做到 70 分”是出题方的描述，不能当成可靠工期或评分依据。实际评分细则没有给出，我们后续应围绕明确要求和可演示的证据来设计。

这轮先给你一个整体构思，不写代码，也不替你把五道架构题直接答完。

**1．先理解它到底在考什么。**

这里的 harness，可以理解成包在模型外面的运行环境：给模型准备上下文、提供工具、执行调用、保存状态、处理错误，并决定什么时候结束。

模型负责判断“下一步做什么”，程序负责保证“这一步执行得正确、状态记录得清楚”。

题目中的基本循环，就是模型提出工具调用，程序执行并回传结果，再让模型继续判断。官方工具文档也明确把客户端工具的循环交给应用实现。参见 [How tool use works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)，章节 **The tool-use contract**、**The agentic loop (client tools)**。

所以，自行实现 Runtime 与使用模型官方 SDK 并不矛盾；关键是不能把循环、状态管理和执行控制交给现成 Agent 框架。

**2．我倾向于做一个“小而完整、行为可解释”的版本。**

可以考虑三条路线：

| 路线 | 好处 | 代价 |
|---|---|---|
| 命令行交互＋本地持久化 | 最容易把核心逻辑做扎实，方便测试 | 多窗口体验需要明确演示方式 |
| 极简聊天页面＋本地持久化 | 会话切换和 trace 更直观 | 增加一些界面工作 |
| 完整聊天产品＋复杂基础设施 | 展示内容多 | 容易挤占核心可靠性的时间 |

**我推荐先按第一条完成核心，再根据时间加一个极简页面。** 核心设计不依赖界面，之后无需重写。

逻辑上只需要几个清晰的部分：

- **Runtime**：驱动循环，控制调用预算和退出条件。
- **模型适配层**：发送请求，解析回复、工具调用和结束原因。
- **工具注册表**：保存名称、描述、参数 Schema 与执行函数。
- **Session 存储**：保存历史、摘要和会话状态。
- **Context 构建器**：决定本次调用究竟带哪些信息。
- **Trace**：记录执行步骤、结果、耗时和错误。

这些是职责边界，不代表要造六套复杂抽象。

**3．几个容易低估的细节，应当提前定清楚。**

**Session 隔离要贯穿所有状态。**  
不能只把聊天记录分开，却让两个窗口共用待办、摘要或某个全局变量。每次执行都应有明确的用户和 session 归属。

待办究竟属于用户还是会话，题面没有完全说清。为了突出窗口互不影响，笔试版本可以先规定“待办按 session 隔离”，在 README 说明；真实产品则可能选择用户级待办，并显式设计跨会话共享。

**工具调用成功与否，必须以执行结果为准。**  
模型说“已经记下”不等于记录成功。参数校验失败、工具超时、存储失败，都要成为模型能看到的结果，不能继续假装成功。

尤其是 todo 这种有副作用的操作：请求重试时，要考虑是否会重复新增。

**“最大轮次”要区分两种含义。**  
用户可以持续对话，但一次用户请求内部，模型不能无限调用工具。建议限制的是单次请求的模型调用次数，并在触顶时说明已完成和未完成的部分。

**“解析思考过程”不能理解成强制获取模型内部推理。**  
不同 API 暴露的字段不同。可以解析模型实际提供的解释或推理摘要，但不能伪造。执行主流程应依赖结构化工具调用和明确的结束状态，避免靠正则从自由文本里猜动作。

**4．Context 和 memory 应从最简单的正确方案开始。**

我会先把信息分成四类：

| 信息 | 建议处理 |
|---|---|
| 当前请求、最近对话 | 保留在上下文中，支撑追问 |
| 较早的历史 | 压缩为结构化摘要 |
| 待办等业务状态 | 独立持久化，通过工具读取和修改 |
| 完整工具输出与执行日志 | 保留原始记录，按需取回 |

一个重要原则是：**聊天摘要可以帮助模型理解状态，但不能代替待办数据库成为事实来源。**

压缩也不能只是“保留最后十条消息”。应按 token 预算触发，保留目标、约束、关键事实、用户纠正和未完成事项，同时避免拆散尚未闭合的工具调用与结果。

压缩后的质量要用追问验证，例如：

> 很早之前用户说“预算上限 800 元”，压缩后再问“按照刚才的预算重新算”，还能否正确接上？

Anthropic 的 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)，章节 **Context engineering for long-horizon tasks → Compaction / Structured note-taking**，也将历史压缩与外部持久化笔记作为不同机制讨论。

**这道题暂时没有必要引入向量数据库。** 先把会话记忆、结构化状态和基础召回讲清楚，就已经有充分的设计内容。

**5．测试应该围绕“它会怎么失败”来构建。**

工具可以先选最明确的三个：`calculator`、`search`、`todo`。其中 search 可以 mock，但要明确标注数据来源；计算器也不能直接执行任意表达式代码。

我会重点验收这些场景：

| 场景 | 要证明什么 |
|---|---|
| 普通聊天 | 能直接回复，无须强行调用工具 |
| 查询后计算，再记待办 | 能根据前一步结果继续执行 |
| “把刚才那条改到周五” | 能理解带工具的追问 |
| 两个窗口交替聊天 | 历史、摘要、待办不串 |
| 历史压缩后继续追问 | 关键事实和未完成事项仍在 |
| 参数错误、未知工具、超时 | 能恢复或明确报告失败 |
| 模型持续调用工具 | 能受控退出 |
| todo 调用后发生重试 | 不会无意重复写入 |

测试分成两层更合理：

- 用可控的模拟模型响应，稳定覆盖异常和边界。
- 用真实 LLM API 跑少量端到端场景，验证实际工具选择和完整链路。

这样既满足真实 API 要求，也不会把整个测试集建立在模型每次输出都一致的假设上。

**6．架构题可以和实现相互支撑，但不用把它们全实现。**

我的初步选题倾向是：

| 模块 | 倾向选择 | 后续讨论重点 |
|---|---|---|
| Context / Performance | 200 轮后的压缩 | 保什么、丢什么、如何验证连续性 |
| Memory | 半个月后重复提问 | 召回时机、相关性、时效性、隐私边界 |
| Task | 长程任务忘记目标 | 外部任务状态、检查点、恢复与进度验证 |
| Tool / Session Runtime | busy 时收到消息或事件 | 事件排队、串行更新状态、打断策略 |
| 架构对比 | 暂不定 | 根据你更熟悉的协议或源码选择 |

模块五尤其要谨慎：**Claude Code 是应用，OpenAI-compatible function calling 是接口约定，直接对比容易混淆层次。** 需要先界定题目指的是模型响应协议、工具结果回传，还是应用运行时行为，再核对具体版本。

模块一的“稳定压到 2 秒”也有隐藏前提：是首次可见反馈，还是实质答案的首 token？冷请求还是缓存命中？这些条件不清楚，就不能直接承诺性能数字。

**7．提交材料应该留下你自己的判断。**

README 应让评审快速找到：如何启动、如何恢复 session、如何验证隔离、context 怎么构建、memory 何时召回，以及已知限制。

## 006 · 助手 · 2026-10-19T00:42:48.209Z

**你的方向合理，适合作为这个项目的总体框架。** 把架构思考穿插在实现中也可行：每做一个机制，就讨论它解决什么问题、有哪些取舍，再用运行结果验证。这样之后写架构题时，有自己的实现依据。

不过，我建议先校准三个边界，避免后面职责混乱。

**第一，`Agent = LLM + 工具 + 上下文 + Harness` 适合作为理解公式，但这四项不是完全独立的模块。**

我的理解是：

- **LLM**：根据当前信息提出下一步行动或回答。
- **工具**：提供可执行的能力，包括查询知识和改变外部状态。
- **上下文**：模型本次决策能够看到的信息。
- **Harness**：组织上述三者，管理它们如何循环、执行、保存和恢复。

这里，Harness 会负责构建上下文、调度模型和执行工具，所以它与前面三项存在组织关系。**你的四个部分更适合作为设计视角，不必直接对应四个代码目录或四个独立子系统。**

**第二，你提出的前三部分，可以这样明确职责。**

| 部分 | 核心问题 | 最小版本应该负责什么 |
|---|---|---|
| 决策与上下文 | 这一步让模型看到什么，模型如何选择下一步？ | 指令、历史与摘要的组织；模型调用；回复与工具调用的解析 |
| 知识与能力 | 有哪些信息可查、哪些动作可做？ | 工具注册、描述与参数 Schema；查询能力；todo 等结构化状态 |
| 执行与运行时 | 如何把模型的选择可靠地执行下去？ | Agent 循环、session 隔离、参数校验、异常处理、调用预算、持久化与 trace |

这里有两个特别重要的区分。

**“模型应该知道什么”由程序和模型共同完成。** 程序先提供必要信息和可用工具；模型发现信息不足时，再通过工具补充。不能完全依赖模型自己发现遗漏，因为它可能根本不知道存在某条约束或某份资料。

**“模型决定调用”与“运行时允许执行”是两件事。** 模型可以提出一个操作，但参数是否合法、当前 session 能否访问目标数据、是否超出执行限制，都应由运行时检查。这也是你第三部分“安全执行”的实际落点。

另外，工具的**定义**属于能力层，工具的**执行控制**属于运行时，两边通过明确接口连接即可。

**第三，第四部分可以暂缓建设，但基本评估必须保留。**

“评估与进化”里面其实包含两个层次：

- 验证当前版本是否正确：测试、场景验收、失败记录。
- 根据评估持续改变 Agent：自动发现缺陷、修改策略或代码、回归验证。

> 原始参数 → 允许的规范化 → 校验 → 权限检查 → 执行。

- 调整前后分别是什么。

|---|---|
| 错误类型与原因 | 知道失败发生在哪里 |
| 涉及的参数或资源 | 定位需要修改的地方 |
| 合法条件或修复建议 | 知道下一步怎么做 |
| 是否已经产生副作用 | 判断能否安全重试 |
| 是否允许重试 | 避免无效循环或重复操作 |

高危操作是其中一类，另外还包括：

- 工具发现多个候选对象，无法确定用户指的是哪个。
- 缺少只有用户能提供的关键信息。
- 修复需要改变已确认的范围、接受额外费用或承担新的影响。

这里最好区分两种交互：**澄清需求**与**请求授权**。前者解决“不知道用户要什么”，后者解决“知道要做什么，但尚未获准执行”。

**一、循环流程：每次模型调用前，都经过 Runtime 检查。**

基本流程是：

> 接收输入 → 加载 session 与任务状态 → 检查控制指令、执行预算和上下文 → 调用模型 → 解析输出 → 执行工具或交还用户 → 保存状态 → 继续循环。

模型输出需要区分几种情况：

| 输出或事件 | Runtime 行为 |
|---|---|
| 请求工具调用 | 校验参数、检查权限、执行、保存结果，再继续 |
| 请求研究子 Agent | 启动受限研究循环，接收结果后继续 |
| 需要澄清或授权 | 保存进度，进入等待用户状态 |
| 给出最终回答 | 检查是否完成约定目标，记录完成或未完成状态 |
| 用户停止、预算耗尽、不可恢复错误 | 受控退出，保存进度并说明原因 |

**等待用户不等于任务完成，循环结束也不等于任务成功。** 排队中的普通消息不能自动被当成授权；针对当前任务的确认，则应能恢复等待中的任务。

这里需要明确三个单位：

- **对话轮次**：用户和 Agent 之间的交互次数。
- **模型调用次数**：一次任务执行内部，模型被调用多少次。
- **工具调用次数**：一次模型响应可能请求多个工具，所以它与模型调用次数不同。

**一、模型决定结束，但必须明确结束原因。**

模型可以判断无需继续调用工具，不过返回结果需要区分：

- **已完成**：满足已确认的目标，有执行结果或证据支撑。
- **等待用户**：需要澄清、授权或补充信息。
- **部分完成**：已有结果，但存在无法解决的缺口。
- **执行暂停**：预算、用户停止或系统问题导致中断。

Runtime 根据这些结果更新状态，不能把“模型停止输出”直接等同于任务完成。

**二、最大轮次限制一次执行，不必限制整个任务的生命周期。**

你担心复杂任务超过 10 次调用，这个问题可以通过**分段执行**解决：

> 执行一段 → 保存检查点并汇报 → 用户选择继续 → 分配新预算 → 从检查点恢复。

用户继续时，不需要重新对齐已经确认的需求，也不应该重复执行完成的步骤。

同时保存两套计数：

- **本次执行消耗**：控制这一段运行。
- **整个任务累计消耗**：避免不断重置计数，让长任务变成无限执行。

“10 次”先作为可配置值，之后根据实际场景调整。模型不能自行重置或扩大预算；主 Agent、研究子 Agent、纠错、重试和压缩的消耗都要计入。

到达软阈值时，可以向模型追加这样的运行提示：

> 剩余预算有限。请判断是否能在剩余预算内完成当前目标。避免启动无法在预算内完成的新工作；如无法完成，保存已有成果、未完成事项、阻塞原因和建议下一步，不得将部分完成表述为完成。

- 最终回复所需的输出空间。
- 必要的状态保存。
- 可能需要的一次收尾调用。

每次发起模型或工具调用前，Runtime 检查剩余预算，设置输出上限和超时。已发出的外部请求可能继续计费，因此费用控制需要预估和预留，不能只在返回后检查。

- 获得了新的有效证据。

搜索和阅读通常不修改业务数据，但仍可能有进展。反过来，模型不断改写搜索词，却始终得到同样的无关内容，也可能没有进展。
