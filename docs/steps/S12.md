## 实际核心代码

结果区分“当前事实”和“本次是否改变事实”：

```python
class TodoCompletionResult(BaseModel):
    model_config = ConfigDict(strict=True, frozen=True, extra="forbid")
    item: TodoItem
    changed: bool
```

完整完成方法为：

```python
def complete(self, context: ExecutionContext, item_id: UUID) -> TodoCompletionResult:
    checked = self._sessions.check_access(context)
    if not isinstance(item_id, UUID):
        raise TypeError("item_id 必须是 UUID")
    with self._lock:
        items = self._items.get(checked.session_id, {})
        current = items.get(item_id)
        if current is None:
            raise KeyError("当前会话中未找到todo")
        if current.status == "completed":
            return TodoCompletionResult(item=current.model_copy(deep=True), changed=False)
        completed = TodoItem.model_validate({**current.model_dump(), "status": "completed"})
        items[item_id] = completed
        return TodoCompletionResult(item=completed.model_copy(deep=True), changed=True)
```

归属检查在已完成分支之前：即使无需改状态，错误owner也不能读取已完成记录。非UUID参数TypeError；无效owner/session是PermissionError；未知或其他session的UUID统一KeyError，不回显标识。不会全局搜索ID，不会自动新增记录。

在同一RLock内查找、判断及替换，所以两个线程竞争同一todo，只有一个能观察到pending并返回changed=True。首次转换保留当前完整字段并重新校验，只覆盖status；更新原字典键保留顺序。已完成分支没有重新赋值，不重置字段或增加副作用。返回冻结副本，旧列表和记录快照仍保持原值。

## 一次具体数据流

1. A会话新增两个“写周报”，ID不同；B也保存自己的记录。
2. complete(A, 第一条ID)先验归属，再在A桶查到pending记录，转为completed，返回changed=True。
3. 再次complete同一ID读到completed，返回相同业务记录、changed=False；A第二条仍pending，B不变。
4. update将已完成项改为“完成后修改标题”，保留completed；随后complete返回该最新标题、changed=False，不拿旧快照覆盖。
5. A使用B的ID、错误owner使用A的ID都被拒绝。todo完成与SessionStore的一次调用任务不同，手动演示中的TaskState仍为running，历史也没有变化。

上述真实内存服务流程已用隔离解释器直接运行，退出0，没有fake模型、真实LLM、凭据读取或外发。

## Python机制与C++类比

- TodoItem的Literal现在允许两个状态；类型注解不自动提供运行时防护，Pydantic构造/重新校验负责限制数据。可类比C++枚举，但两者的检查时机不同。
- TodoCompletionResult接近包含值对象和bool的结果struct；冻结阻止正常字段赋值，深副本隔离返回值与保存值。它不是防止任意进程内Python代码篡改的安全沙箱。
- `with self._lock`接近RAII作用域锁，异常也会释放，不依赖Python对象析构时机。把“检查是否已完成”和“设置已完成”放在同一作用域，避免两个线程都报告首次变化。
- 字典展开复制当前字段后覆盖status，再model_validate，避免使用跳过校验的model_copy(update=...)修改内部状态。返回时普通深副本不含未经校验的更新。

## 幂等、替代方案与取舍

本步幂等针对业务状态：完成一次和完成多次之后保存的记录相同，即C(C(s))=C(s)。响应中的changed可以不同：首次True、之后False，它描述本次转换，不是新增业务字段。

仅仅每次无条件把status写成completed，也能让最终状态值相同；但不能区分首次变化和重复调用，附带的计数/事件若每次执行仍会重复。本实现显式跳过已完成写入，不添加本步没有需求的计数器或事件来制造验收点。测试通过公开接口核对changed、完整记录及列表，没有窥探私有字典或mock写入次数。

合理替代一是只返回TodoItem，类型更少；调用方若想知道本次是否变化，需要额外读取，而且读后写存在竞争。选择小结果对象，在锁内确定changed，代价是多一层返回结构。

替代二是持久化操作ID与事务化去重，能处理新增操作或网络结果丢失后的恢复，但需要存储及更明确的重试语义；本步不提前实现S25。changed标志也不能独自保证外部通知恰好一次：状态变化后进程崩溃、或外部动作失败，仍需后续事务/恢复设计。未来S40的提醒联动尚未实施。

目前仅同一服务实例、同一进程内的状态转换；重启无恢复、无跨进程锁或真实登录。模型业务授权仍在S16接入，不把todo完成等同于整个Agent目标已达成。未实现重新打开、删除、日期或提醒。
