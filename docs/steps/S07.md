## 接口与结果表示

`ToolRegistry.execute(call: ToolCall) -> dict[str, object]` 接受已经过边界校验的ToolCall，负责按名称查找、参数模型校验及显式调用handler。注册/get/schemas仍不执行handler。execute返回成功或可修正错误；handler异常继续传播，交Runtime停止。

Runtime将结果用 `json.dumps(..., ensure_ascii=False, allow_nan=False)` 写入tool消息的content。S06的裸文本成功结果在本步统一为JSON封装，Message本身的结构不变：

```json
{"ok": true, "result": "0.3"}
```

未知工具的实际错误形状为：

```json
{
  "ok": false,
  "error": {
    "code": "unknown_tool",
    "message": "工具未注册，请选择可用工具。",
    "execution_state": "not_started",
    "recovery": "correct_request_with_new_id",
    "available_tools": ["calculator"]
  }
}
```

参数错误使用code=invalid_arguments，另有issues和expected_schema：issues标明已注册参数模型的顶层字段，其他位置用 `<extra>`；expected_schema是已有模型可见Schema，包含必填、类型、范围和额外字段约束。原始input/ctx/msg、未知字段名和异常堆栈不进入错误正文。

这里只提供顶层字段定位；嵌套精细路径、根级校验的细分类别和自定义业务校验的额外条件没有自动推导。后者需要工具公开说明明确表达，不能从可能含私密输入的异常正文中直接提取。

## 实际核心代码

执行入口先区分未知工具与参数错误：

```python
try:
    tool = self.get(call.name)
except KeyError:
    return _request_error(
        "unknown_tool", "工具未注册，请选择可用工具。",
        available_tools=list(self._tools),
    )
try:
    arguments = tool.parameters.model_validate(call.arguments)
except ValidationError as error:
    # 原始 input、ctx、msg 和额外字段名都可能夹带私密输入。
    issues = []
    for issue in error.errors(include_input=False, include_context=False, include_url=False):
        location = issue["loc"]
        field = location[0] if location and location[0] in tool.parameters.model_fields else "<extra>"
        issues.append({"field": field, "reason": "不符合参数 Schema"})
    return _request_error(
        "invalid_arguments", "参数校验失败，请按 Schema 修正。",
        issues=issues, expected_schema=tool.parameters.model_json_schema(),
    )
output = tool.handler(**arguments.model_dump())
if not isinstance(output, str):
    raise InvalidToolResultError("工具结果必须是字符串")
return {"ok": True, "result": output}
```

ValidationError的捕获范围只包参数校验。handler内部即使抛出同名ValidationError，也属于执行阶段异常，不会被伪装为“尚未执行”。`_request_error`只生成数据，不执行工具或调用模型。

Runtime在整批执行前检查所有ID是否与已用ID冲突，然后只写一条包含整批请求的assistant消息。每个请求的实际处理是：

```python
had_request_errors = False
for call in response.tool_calls:
    seen_call_ids.add(call.id)
    try:
        outcome = self._tools.execute(call)
        output = json.dumps(outcome, ensure_ascii=False, allow_nan=False)
    except InvalidToolResultError:
        return RunResult(
            status="failed", response=response, error_code="invalid_tool_result"
        )
    except Exception:
        return RunResult(
            status="failed", response=response, error_code="tool_execution_failed"
        )
    messages.append(Message(role="tool", content=output, tool_call_id=call.id))
    had_request_errors |= outcome["ok"] is False
```

普通请求错误生成一条结果后继续处理兄弟调用，所以有效请求不会因另一个未知工具或非法参数被漏掉。只有完整处理完当前批次，才再次调用模型。handler异常/非文本返回值则立即停止剩余调用；已经完成的调用没有回滚，也不重放。

修正轮数通过 `Runtime(..., max_tool_error_rounds=2)` 配置，只接受非负整数且拒绝bool。默认最多允许两批请求错误进入后续模型调用，第三批错误处理完后停止：

```python
if had_request_errors:
    if error_rounds >= self._max_tool_error_rounds:
        return RunResult(
            status="partial", response=response, error_code="tool_repair_limit"
        )
    error_rounds += 1
```

一个批次无论有几个请求错误，只计一次修正机会；成功批次不清零累计计数。设为0时仍允许正常成功链路，但第一次错误后不再调用模型。检查发生在当前批次完成后，所以同批的有效兄弟调用仍会执行。这是修正回传上限，不是工具调用配额或S19的完整硬预算。

最近一批仍有请求错误时，下一轮stop保留正文但返回partial/tool_request_failed，避免只因为模型声称完成就报告完成。后续一个全成功工具批次会清除这条机械阻挡；它并不证明每个业务目标已修复，完整目标状态和授权在后续步骤实现。

## 一次具体的数据流

本地演示使用脚本化模型和真实calculator：

1. 第一轮同时提出bad：expression=123，以及good：expression="0.1+0.2"。
2. bad在参数校验阶段失败，handler未执行；good实际计算得到"0.3"。
3. 第二轮输入包含一条assistant双请求消息，加bad与good两条tool结果，顺序与ID一一对应。
4. 模型脚本提出新ID fixed：expression="2+3"，Runtime实际得到"5"并回传。
5. 第三轮模型输出stop，Runtime返回completed。

模型的修正决策是脚本预设，不代表真实LLM会自主理解错误。工具数值结果来自实际calculator，不是预设替身结果。

## 边界与取舍

| 选择 | 合理替代方案 | 本步取舍 |
| --- | --- | --- |
| 按列表串行执行 | 并发收集结果 | 请求/结果顺序和副作用归属容易检查；延迟累加，没有并行收益 |
| 每调用一个JSON结果 | 裸字符串或整批只返回一个错误 | 成功与错误可明确区分、保留各ID；封装略增加消息长度，S06断言须同步更新 |
| 未执行请求错误可修正 | 所有异常均让模型重试 | 校验错误不会执行handler；执行后异常无法据此推断副作用状态，继续停止 |
| 明确Schema加固定字段说明 | 直接返回ValidationError字符串 | 保留合法条件且不回显私密输入；自定义业务错误的细节更少，Schema有重复开销 |
| 整批ID预检 | 执行到重复项才检查 | 新调用不会在同批旧ID被发现前先执行；不是持久幂等或事务 |
| 有限错误回传 | 无上限让模型继续修正 | 最多两轮默认修正；达到上限保留partial，尚不能持久恢复 |

Python `for`可类比C++中按顺序遍历请求vector并查函数表，`dict`结果类似带成功/错误标签的结构体；这里的dict类型注解不提供运行时结构校验，结果由可信注册表代码构造，JSON序列化拒绝不兼容值。固定错误码与抛异常各有职责：前者告诉模型可以改请求，后者让Runtime停止结果不确定的执行。

S06的截断/拒绝/模型错误不执行夹带请求、消息快照、响应重校验、进程中断传播均保持。除零也仍走calculator的handler异常停止路径；本步不把所有ValueError自动认作安全可重试。

仍无通用成功轮次上限、主动超时、持久检查点、完整权限策略或trace。RunResult没有完整历史；达到修正上限时，最后批次结果只存在于当前运行的内存历史，不会再送模型或作为持久进度返回。S08再加入结构化诊断，S19负责整体预算。没有读取密钥或外发数据。
