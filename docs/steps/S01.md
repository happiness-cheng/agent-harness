## 先写测试，再观察失败

实际测试完整内容：

```python
import subprocess
import sys


def test_installed_package_imports_outside_project(tmp_path):
    result = subprocess.run(
        [sys.executable, "-I", "-B", "-c", "import min_agent"],
        cwd=tmp_path,
        capture_output=True,
        text=True,
        timeout=10,
    )

    assert result.returncode == 0, result.stderr
```

具体数据流：pytest 调用测试 → 提供临时目录 tmp_path → 子进程使用当前虚拟环境的 sys.executable → 切换到项目外目录 → 执行 import → 将退出码和 stderr 返回测试 → 断言退出码为 0。

- tmp_path 是 pytest 提供的 Path 对象；函数参数名使 pytest 注入临时目录，并非业务代码自行查找参数。
- sys.executable 是正在运行 pytest 的解释器路径，避免误调用 PATH 中的 MSYS2 Python。
- `-I` 启用隔离模式，忽略 PYTHONPATH、用户 site-packages 和当前目录等干扰，仍使用这个虚拟环境的 site-packages。这样只有当前环境正确安装后才能找到我们的 src 包。
- `-B` 不让导入子进程写 pyc；它不禁止 Python 读取已有字节码。
- capture_output 收集输出，失败时通过 result.stderr 显示真实原因。正常 import 没有输出，因此不依赖某句欢迎语判断成功。
- timeout=10 限制子进程等待；超时会报 TimeoutExpired，和找不到包是不同故障。

首次运行时包入口和项目配置尚不存在。实际输出为 `ModuleNotFoundError: No module named 'min_agent'`、`1 failed in 0.71s`，退出码 1。失败来自缺失的目标行为，测试框架本身已可运行。

本步没有可供校验的业务输入，故不编造非法参数测试；边界是“从项目外、在隔离解释器中也可导入”，未安装时的 RED 记录证明失败路径。此测试不能证明后续模型、工具或网络行为。

## 最小实现

pyproject.toml 的完整核心配置：

```toml
[build-system]
requires = ["setuptools==84.0.0"]
build-backend = "setuptools.build_meta"

[project]
name = "agent-harness"
version = "0.1.0"
description = "以小步测试构建的 Python Agent Harness"
requires-python = ">=3.13"
dependencies = []

[project.optional-dependencies]
dev = ["pytest==9.1.1"]

[tool.setuptools.packages.find]
where = ["src"]
namespaces = false

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = '--strict-markers -m "not live"'
markers = ["live: 需要显式授权和凭据的真实外部调用测试"]
```

`build-system` 告诉 pip 用哪个构建后端；`project` 描述可安装的发行包；`packages.find` 指定从 src 寻找普通包；pytest 配置提供默认收集路径和严格标记检查。dev 是可选开发依赖，运行时 dependencies 当前为空。

发行名 agent-harness 用于 pip/包元数据；导入名 min_agent 用于 Python import，两者不必相同。前者描述发布产物，后者对应源码目录。

默认排除 live 的标记不代替权限检查，也无法阻止模块收集阶段的顶层网络代码。后续 live 测试仍必须把外部操作放进显式启用的测试执行阶段。本步没有任何外部调用测试，也没有验证真实模型。

包入口完整实现只有一行：

```python
"""自写 Agent Harness 的 Python 包。"""
```

__init__.py 将目录声明为普通包。当前不需要函数、类、版本常量或导入时副作用；先保证后续代码有可验证的安装入口。

## 设计原因、替代方案与取舍

选择 src 布局：源码与项目工作目录分开，需要先安装再导入，能早点发现包发现和安装配置问题。替代方案是在根目录直接放 min_agent.py，初始更省事，但容易因当前目录在搜索路径里而掩盖安装错误。代价是多一层目录以及一次安装操作。

开发时用 editable 安装：site-packages 中的安装记录指向 src，修改源码后无需每次重新安装。替代方案是每步构建 wheel 并重新安装，较接近分发环境但反馈更慢。本步另行构建普通 wheel，并检查它实际包含包入口；未在另一干净机器验证安装。

pytest 测试用真实子进程而非 mock import，也不修改 sys.path。代价是比进程内 import 多一点启动时间，收益是能观察当前环境下真实的包发现行为。

C++ 类比：pyproject.toml 有一点像构建/依赖声明，src/min_agent 像独立库的源码目录；这只是职责类比。Python import 会在运行时加载并执行模块，之后通常由 sys.modules 缓存，不等于 C++ 的头文件文本包含或链接过程。

## 原生环境与安装异常

MSI 安装器的官方哈希与 Windows 签名校验均成功，但安装返回 1622。日志将旧 Python 3.13.5 识别为 MajorUpgrade，因此不继续沿该路线安装。具体日志打开失败的底层原因未确定，没有冒称修复 MSI 故障。

最终使用 Python Software Foundation 的同版本官方 NuGet 包，在独立目录解包；python.exe / python313.dll 签名均 Valid。实际解释器为 win-amd64、Python 3.13.16，并能在默认 TLS 校验下访问 PyPI（HTTP 200）。保留失败日志和下载缓存，不删除用户旧环境。

依据：[Python Windows §4.3 The nuget.org packages](https://docs.python.org/3.13/using/windows.html#the-nuget-org-packages)、[Python 3.13.16 §Files](https://www.python.org/downloads/release/python-31316/)、[setuptools §Development Mode](https://setuptools.pypa.io/en/latest/userguide/quickstart.html#development-mode)、[pytest §Choosing a test layout](https://docs.pytest.org/en/stable/explanation/goodpractices.html#choosing-a-test-layout)。
