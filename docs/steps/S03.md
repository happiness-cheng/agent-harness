## 接口与核心代码

工具配置是一个小的值容器：

```python
@dataclass(frozen=True)
class ToolDefinition:
    name: str
    description: str
    parameters: type[BaseModel]
    handler: Callable[..., object]
```

dataclass 自动生成初始化等常规方法；frozen=True 禁止直接替换字段。它由可信应用代码创建，类型注解本身不校验输入，必要的配置检查在 register 中进行。parameters 保存参数模型“类”，不需要先构造某次调用的参数值；handler 保存可调用对象，不在注册时调用。

Callable[..., object] 表示本步仅承诺保存一个 callable，不假装已经检查函数签名或返回值。将来工具执行层还要规定实参、结果及同步/异步行为。

注册逻辑完整如下：

```python
def register(self, tool: ToolDefinition) -> None:
    if not isinstance(tool.name, str) or not tool.name.strip():
        raise ValueError("工具名称必须是非空白字符串")
    if tool.name in self._tools:
        raise ValueError(f"工具名称重复：{tool.name}")
    if not isinstance(tool.description, str) or not tool.description.strip():
        raise ValueError("工具描述必须是非空白字符串")
    if (
        not isinstance(tool.parameters, type)
        or not issubclass(tool.parameters, BaseModel)
        or tool.parameters is BaseModel
    ):
        raise TypeError("parameters 必须是具体的 Pydantic 模型类")
    if not callable(tool.handler):
        raise TypeError("handler 必须可调用")
    if tool.parameters.model_json_schema().get("type") != "object":
        raise ValueError("工具参数 Schema 顶层必须是对象")

    self._tools[tool.name] = tool
```

所有检查在字典写入之前，因此重复名或非法配置不会覆盖已有工具，也不会留下半个注册记录。strip 只用于判断是否空白，不静默改写工具名；查找按原名称精确匹配。Schema 生成失败也会在写入前暴露。

实例自己的字典以及查找/导出：

```python
def __init__(self) -> None:
    self._tools: dict[str, ToolDefinition] = {}

def get(self, name: str) -> ToolDefinition:
    return self._tools[name]

def schemas(self) -> list[dict[str, object]]:
    return [
        {
            "name": tool.name,
            "description": tool.description,
            "parameters": tool.parameters.model_json_schema(),
        }
        for tool in self._tools.values()
    ]
```

未知名称沿用 Python 字典的 KeyError，其中保留请求的名称；没有不明确的 None 结果。每个注册表有独立字典，避免实例间共享工具集合。Python dict 保留插入顺序，因此导出顺序可预测。

schemas 只输出三个模型可见字段，handler 和 Python 模型类不进入 JSON。每次生成新列表、字典和 Schema；测试实际修改深层属性后再次导出，验证原定义没有被污染。没有实现 provider 专用的 function 包装，S17 适配器再处理具体 API 格式。

## 测试和具体数据流

测试参数模型：

```python
class ExpressionArguments(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    expression: str = Field(min_length=1, description="待计算的表达式")
```

数据流：可信代码创建参数类和 handler → 构造 ToolDefinition → register 校验配置后存入字典 → schemas 导出名称/描述及参数类生成的 JSON Schema → get 按同一名称取回本地配置。取回后仍没有执行工具。

测试使用 sentinel_handler：一旦调用就抛 AssertionError。注册、查询、Schema 导出均通过，证明这些操作没有启动 handler。另用真实 Python 进程注册 demo 定义、导出 JSON、取回同一个 handler 并查询 missing，观察到预期 KeyError 和 handler 执行次数为 0。这些是本地注册表验证，不是 calculator 或真实模型工具选择验收。

18 项行为测试覆盖：

- 空表、登记后可查、多个工具的注册顺序。
- 导出元数据仅含名称/描述/Schema，保留字段说明、必填项及参数约束，可 JSON 序列化。
- 重复注册不替换原定义，未知工具报告名称。
- 修改导出数据不会污染下一次结果；两个实例不共享注册状态。
- 空白/错误类型的元数据、非法参数类、非对象 Schema、不可调用 handler 均拒绝，失败不留下记录。

## 方案取舍与 C++ 类比

选择实例内字典，而不是全局装饰器自动注册：按名称查找直接，重复项和加载顺序明确，测试容易隔离。全局装饰器减少显式注册代码，但会让导入顺序带来副作用，当前三个基础工具不需要自动发现平台。

Schema 由已有 Pydantic 参数类生成，避免参数校验和手写 JSON Schema 各维护一份。代价是参数定义依赖 Pydantic；本步复用已有依赖，没有重造 JSON Schema 生成器或校验器。

本地配置使用 dataclass，而不是把 handler 塞进 S02 的模型输入对象：这里保存 Python 类和函数，来自可信代码；模型输入则使用严格 Pydantic 数据契约。模型看不到 handler，也不能通过返回 JSON 注册自己的函数。

C++ 类比：ToolDefinition 接近保存元数据及 std::function 的 struct，字典查找接近 unordered_map；Python 函数是可直接保存的对象。差异是 Python dict 保持插入顺序，unordered_map 不保证；Python 注解不提供 C++ 编译期签名检查。frozen dataclass 也不等于所有引用内容都深层 const。

## 局限与审阅停点

注册只证明配置可登记，不证明 handler 的签名/返回值与参数类匹配，不代表有执行权限。工具实参、错误回传和调用/结果配对留给后续 Runtime 步骤。当前不支持并发注册，也未提供动态注销或插件发现。
