## 接口与消息契约

```python
class Model(Protocol):
    def generate(
        self, messages: list[Message], *, tools: list[dict[str, object]] | None = None
    ) -> ModelResponse: ...
```

模型协议新增 keyword-only 的 tools：调用时必须写 `tools=...`，避免与消息参数的位置混淆。`Runtime(model, tools=registry)` 每次向模型提供注册表导出的元数据；handler 不进入Schema。未注入注册表时仍使用 S05 的单参数调用形式，工具请求返回 partial/tool_execution_not_supported。

Message 新增 `tool_calls: list[ToolCall] = Field(default_factory=list)`；只有 assistant 消息能包含非空请求列表，同一消息内的调用ID不可重复。tool 消息仍必须包含 tool_call_id，content 仍是字符串。模型没有工具前导正文时，assistant 历史消息的正文用空串；没有改成新的可空文本体系。ToolCall 定义移到 Message 前面，字段契约本身不变。

这里只做单条消息的校验；跨消息配对顺序由 Runtime 构建。它不是通用任意聊天历史校验器。

## 实际核心代码

每次 run 重新创建 messages 和 seen_call_ids，while 每一轮重新调用模型。模型收到独立消息快照，不能直接修改 Runtime 保留的历史：

```python
messages = [Message(role="user", content=text)]
seen_call_ids: set[str] = set()
while True:
    try:
        model_messages = [message.model_copy(deep=True) for message in messages]
        if self._tools is None:
            response = self._model.generate(model_messages)
        else:
            response = self._model.generate(model_messages, tools=self._tools.schemas())
    except Exception:
        # 异常正文可能含请求或凭据；结构化诊断在 S08 接入。
        return RunResult(status="failed", error_code="model_call_failed")
```

循环里的下一段继续使用 S05 的响应类型检查及 `model_dump(warnings="error") → model_validate`。这是每轮都执行的边界校验，不是只验证第一轮。

只有 `finish_reason="tool_calls"` 才进入工具执行分支。注册表存在后，先做本步范围与重复ID检查：

```python
if len(response.tool_calls) != 1:
    return RunResult(
        status="partial", response=response,
        error_code="multiple_tool_calls_not_supported",
    )
call = response.tool_calls[0]
if call.id in seen_call_ids:
    return RunResult(
        status="failed", response=response, error_code="duplicate_tool_call_id"
    )
seen_call_ids.add(call.id)
```

两个请求会在任何 handler 执行前整体返回，不会悄悄只执行第一项。跨轮重复ID在再次执行前停止，避免同一个请求ID对应两次执行。这个集合只属于本次 run，不是持久去重或跨请求幂等系统；另一次 run 可以出现相同ID。

实际执行和结果回传：

```python
try:
    tool = self._tools.get(call.name)
    arguments = tool.parameters.model_validate(call.arguments)
    output = tool.handler(**arguments.model_dump())
except Exception:
    return RunResult(
        status="failed", response=response, error_code="tool_execution_failed"
    )
if not isinstance(output, str):
    return RunResult(
        status="failed", response=response, error_code="invalid_tool_result"
    )
messages.extend([
    Message(
        role="assistant", content=response.content or "",
        tool_calls=response.tool_calls,
    ),
    Message(role="tool", content=output, tool_call_id=call.id),
])
```

`get` 只允许查找注入表中的名称；没有自动发现内置 calculator。Pydantic 参数模型先校验请求，再 `model_dump()` 成关键字参数，`**` 将字段名展开给 handler。具体工具的参数校验与函数签名必须由可信应用配置保持一致，注册阶段未检查所有签名组合。

本步只支持文本工具结果，calculator 返回 `"0.3"` 正好符合契约。没有用 str 把任意对象悄悄变成文本。查找/校验/执行异常返回固定错误码，不打印或返回原异常正文；KeyboardInterrupt 等 BaseException 仍传播。

成功后先写 assistant 请求，再写带 tool_call_id 的 tool 结果；执行流自然进入下一轮 while。下一轮的输入因此包含已执行结果，模型才能继续决定。Runtime 不根据“计算”等关键词自行决定工具，也不拿工具结果替代模型最终回答。

## 一次真实本地 calculator 数据流

脚本第一项预设为请求 `calculator(expression="0.1+0.2", id="calc-1")`，第二项为 stop/结果是0.3：

1. 第一轮模型输入只有 `user: 请计算0.1+0.2`，另有 calculator 的名称、描述和参数Schema。
2. 模型返回工具请求；Runtime 从注入表中找到 CALCULATOR_TOOL，校验 CalculatorArguments。
3. 实际调用 S04 的 calculate，按独立 Decimal Context 计算，得到字符串 `"0.3"`。
4. 第二轮模型输入依次为 user、带 calc-1 请求的 assistant、`tool(content="0.3", tool_call_id="calc-1")`。
5. 模型返回 stop/结果是0.3，Runtime 返回 completed，模型总调用次数为2。

fake 的两项决策是预设的，但步骤3执行了真实 calculator。它证明工具链路与消息配对，没有证明真实LLM会主动正确选择工具或计算规划。

## 状态、失败与限制

stop、length、refusal、error 沿用 S05 规则；工具后续回答也一样。length/refusal/error 即使带工具请求，也不会执行它们。completed 仅表示模型正常回答结束，不保证答案事实正确或复杂业务目标完成。

| 情况 | 本步结果 | 是否再次调用模型 |
| --- | --- | --- |
| 一个有效工具请求，文本执行结果 | 添加请求与结果后继续 | 是 |
| 未注入注册表 | partial / tool_execution_not_supported | 否 |
| 一次多个请求 | partial / multiple_tool_calls_not_supported | 否，且零执行 |
| 同次run跨轮重复ID | failed / duplicate_tool_call_id | 否，重复项零执行 |
| 未知工具、参数错误、handler异常 | failed / tool_execution_failed | 否 |
| handler返回非文本 | failed / invalid_tool_result | 否 |
| 模型异常或非法响应 | failed / model_call_failed 或 invalid_model_response | 否 |

固定错误码只处理停止边界，S07 再实现带调用ID的可修复错误回传。handler 报错或返回不合契约时，不能据此证明它没有产生副作用；本步没有自动重试或回滚。工具执行后的模型调用失败也不会重放工具。RunResult 仍只保存最终响应，不返回完整历史；中途结果目前没有持久检查点，trace在S08实现。

当前 while **没有轮次预算和主动超时**。只用有限本地脚本验收，不读取密钥、不调用真实LLM、不接后台服务；S19 才建立硬预算。不能将本步称为已具备有界自主运行保护。注册表是本地能力清单，不是完整权限策略；写业务状态的工具与模式授权按后续步骤实现。

## Python机制、C++类比与取舍

| 选择 | 合理替代方案 | 原因与代价 |
| --- | --- | --- |
| 同步while驱动每轮决策 | 递归继续调用run / 异步调度框架 | while无递归栈增长、历史归属清楚；同步handler/模型会阻塞，暂时没有取消/超时 |
| 请求消息加结果消息 | 仅追加结果字符串 | 模型能对应工具名称、参数和ID；消息量增加，但避免丢失调用上下文 |
| 根据注册参数类校验再展开handler | 直接传入模型原始字典 | 类型和额外字段错误在执行前拒绝；引入校验开销，注册配置仍需可信 |
| 每次模型调用传深快照 | 共享同一个消息列表 / 浅复制 | 嵌套请求和Schema修改不污染保留状态；多一次复制开销，没有性能基准 |
| S06每响应一个调用、失败停止 | 立即实现批量/并发及错误恢复 | 本步易读且可验证；能力限制明确，恢复需要S07 |

循环可类比 C++ 中“控制循环调用模型接口 → 根据返回枚举调用函数表 → 将结果写回历史”。具体模型决定请求内容，Runtime 控制执行与何时继续；没有另外实现C++版本。

Python `**arguments.model_dump()` 类似把校验后的具名配置适配成一次函数调用，但不具有C++编译期实参匹配保证。Protocol 也不强制运行时继承。普通Python赋值共享引用，所以显式复制消息；这与复制C++值类型的直觉不同。`set[str]` 只做本次run内ID成员判断，不代表事务或副作用幂等。
