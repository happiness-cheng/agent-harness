## 现在的接入方式

可信应用创建SessionStore（需要落盘时显式传storage）、TodoService和TaskController，再调用todo_registry(todos,controller,context)得到当前会话的工具集，交给Runtime.run_session。模型只看到五个Schema，不得到controller、SessionStore、owner/session或模式选择接口。

| 模型工具名 | 真实行为 | 规范化后的ActionSpec |
| --- | --- | --- |
| todo_list | 当前会话普通列表，含完成项与逾期投影、隐藏逻辑删除项 | todo.list，空参数 |
| todo_add | 新增并返回真实记录 | todo.add，title及绝对due_date或null |
| todo_update | 按ID应用patch，省略字段保留，due_date=null清除 | todo.update，规范UUID及实际提供的补丁字段 |
| todo_complete | 完成，重复完成changed=false | todo.complete，规范item_id |
| todo_delete | 逻辑删除，重复删除changed=false | todo.delete，规范item_id |

工具Schema拒绝额外owner_id/session_id/mode等字段。UUID字符串允许按标准解析后转规范字符串；title严格校验。日期标签先校验有效日历日期或今天/明天/后天，再在真实服务同一时钟/时区下解析；实际业务接收绝对日期，不第二次把“明天”按另一个时刻解释。

update的patch用TypedDict(total=False)，经过Pydantic解析仍保留键是否存在；不会把未传due_date补成null。空补丁、title=null和未知字段拒绝。未选全可空字段模型，是因为统一model_dump后容易丢失“省略”和“清空”的区别。

## 实际核心代码与锁边界

TaskController不再各自保存字典；工作状态从SessionStore读取、先提交再发布。实际set_work_state实现：

```python
def set_work_state(self, context: ExecutionContext, state: WorkState) -> None:
    """仅可信控制入口调用；先提交完整候选快照，再发布内存。"""
    with self._lock:
        session = self._session(context)
        if not isinstance(state, WorkState):
            raise TypeError("state必须是WorkState")
        checked = WorkState.model_validate(state.model_dump(warnings=False))
        candidate = session.model_copy(deep=True)
        candidate.work_state = checked
        self._commit_session(candidate)
```

_commit_session沿用S15-b：保存当前完整会话和全部todo成功后才替换内存。模式选择、提案、确认、越界等待都经此路径；SQL失败保留上次提交事实并传播错误。同一store上的多个控制器、业务调用及后续重启不会各持一份旧权限缓存。

真实工具入口先归一化，再判定完全相同的实际参数，摘自_TodoExecutor._run：

```python
with self._todos._sessions.control(self._context):
    if "due_date" in parameters:
        parameters["due_date"] = self._todos.normalize_date(parameters["due_date"])
    normalized = parameters.copy()
    if "item_id" in normalized:
        normalized["item_id"] = str(normalized["item_id"])
    if normalized.get("due_date") is not None:
        normalized["due_date"] = normalized["due_date"].isoformat()
    action = ActionSpec(operation=f"todo.{operation}", parameters=normalized)
```

随后调用实际guard；只有成功进入with主体才运行相应业务handler：

```python
@contextmanager
def guard(self, context: "ExecutionContext", action: ActionSpec):
    """授权检查至真实业务提交保持同一会话锁，不发放可缓存的许可。"""
    with self._sessions.control(context):
        decision = self.authorize(context, action)
        if not decision.allowed:
            raise AuthorizationRequired(decision.code)
        yield
```

共享SessionStore的同一把RLock覆盖归一化、检查与业务提交；不是把allowed=True缓存后再执行。模型调用期间用户改为Plan，返回后的写操作会被拦住。已经取得锁开始执行的写操作先完成，随后模式切换才生效；不承诺撤销既有提交。目前该锁覆盖整个store，不同session的写也串行，代价是吞吐受限。

内存TodoService仍各有独立业务集合，但改为共用store锁，避免一个线程持todo锁等session锁、另一个持session锁等todo锁的反向顺序。持久化模式仍共享既有完整todo集合。锁后继续验证业务ID归属；即便确认清单出现别的session的ID，真实服务仍拒绝操作。

可类比C++在一个lock_guard/recursive_mutex作用域内完成检查和受保护操作。候选WorkState可类比临时值，SQLite提交成功后发布；深复制和重新解析继续隔离嵌套JSON别名。TYPE_CHECKING只供类型引用，避免sessions导入WorkState后又反向运行时导入sessions；类型注解不替代Pydantic验证。

## Runtime等待、会话绑定和继续

ToolRegistry绑定实际SessionStore对象和ExecutionContext。Runtime在begin/调用模型前核对同一对象及owner/session；错会话、错store或对绑定工具用无上下文run均拒绝。原不绑定的calculator等工具链消息契约保留。应用可在返回的绑定registry中注册calculator，不能把绑定handler抽走另组无约束入口后仍宣称受本契约保护。

AuthorizationRequired与普通参数错误分开。Runtime新增waiting_user结果，单次TaskState与trace也支持该状态；遇到阻断不继续让模型“修正参数”绕权限。实际批次处理片段：

```python
for blocked in response.tool_calls[index:]:
    messages.append(Message(
        role="tool", tool_call_id=blocked.id,
        content=json.dumps({"ok": False, "error": {
            "code": error.code if blocked.id == call.id else "waiting_user",
            "message": "等待用户确认或模式选择；该请求未执行。",
            "execution_state": "not_started",
            "recovery": "directed_user_confirmation",
        }}, ensure_ascii=False),
    ))
return RunResult(status="waiting_user", response=response, error_code=error.code)
```

此前成功执行的结果保持；当前及后续未执行请求都有配对结果。后续handler不启动，也不再调用模型。尝试执行而被授权阻断的tool trace及run trace记waiting_user/not_started；后续跳过请求在消息里明确not_started，没有伪造执行span。

示例：同一响应要求“新增已确认A、再新增越界B、再新增A”。第一个A真实提交，B前停止，第三个不启动；三个请求均有结果，返回waiting_user。确认后新run_session可继续，旧请求不会由程序自动重放。模型以后重新提出同参数新增仍可能产生新记录，本步未提供执行配额/幂等键；S25另处理重试/未知结果，不能把“未自动重放”说成恰好一次。

WorkState.mode、目标确认/等待，与单次TaskState.status仍独立。例如Plan禁止写导致单次运行waiting_user，WorkState可能仍为Plan/ready；这是需要用户选择模式，不等于自动改变或确认目标。Build越界则WorkState也保存scope_not_confirmed等待。确认不把Plan升Build，也不执行任何工具。再次run_session是新的显式执行片段，不是队列自动派发；S22尚未实施。

SQL失败不能伪装成授权等待或操作成功。授权等待状态本身保存失败会传播；真实业务SQL失败也传播/被Runtime按现有失败路径处理，保留上次已提交状态。通用执行异常仍保守记结果unknown，并未实现S25的核对恢复。Runtime begin/append/finish仍分别提交，不是整次模型运行的一次数据库事务。

## 系统规则与模型输入

src/min_agent/prompts/system.md包含身份、需求对齐、模式、当前能力、工具/失败和完成判断骨架。pyproject的package-data把它装入wheel，Runtime按包资源读取，不依赖工作目录。仅绑定会话工具链启用该规则，静态正文在Runtime构造时读取。

每次模型请求前读当前工作状态：静态system前缀 + user角色的application_state JSON数据投影 + 原对话消息。目标文本不升级成system指令，身份/模式不能从模型字段取得；投影不保存进原聊天，避免重复污染历史。实际工具入口始终复查，不因提示词或投影说“已允许”就放行。这里没有隐藏思维链、模型分类器或自然语言确认解析。

提示词写明日期todo不等于主动提醒、工具实际结果才是业务依据、completed只表示本执行片段正常结束；即使模型stop，仍不能据此声称用户目标完成。未做S17真实模型协议/账号验收或S18语义案例，也未承诺新Schema已适配某个提供商的严格函数调用格式。
