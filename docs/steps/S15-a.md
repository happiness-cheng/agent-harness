## 数据与接口

- sessions：session_id主键、owner_id、snapshot_json，保存已有消息与当前TaskState事实。
- todos：session_id/todo_id联合主键、position顺序及item_json；外键引用sessions，位置非负且同session唯一。JSON保留due_date、pending/completed和deleted；不保存overdue投影、不物理删除行。
- create_new(path)：排他新建，已有文件连空文件也拒绝；初始化失败不擅自删除残留文件。父目录由可信入口准备。
- open(path)：URI mode=rw，缺失文件不自动创建；应用标识、版本及表结构不符则拒绝，不自动修复或迁移。
- save(context,snapshot,todos)：同一事务保存一个会话与完整待办集合，重新校验现有Pydantic模型。已有owner不可改；输入必须同session、ID唯一，已有todo不得遗漏/重排，旧已删项不可恢复/改写，完成项不可改回pending。
- load(context)：按owner/session查询，未知与越权统一PermissionError；索引与JSON内容不一致、顺序断裂、无效JSON或业务模型拒绝读取。
- load_all()：可信应用启动入口，不向模型或普通业务请求暴露；检查外键及全部记录后才返回，不跳过损坏行。
- StoredSession(snapshot,todos)：脱离存储的返回值；字段容器冻结，但嵌套快照/列表仍可在本地修改，只有再次显式save才会落盘。

StoredSession复用SessionStore现有静态工具配对检查（当前为内部接口），避免持久化放宽会话约束。running/failed/partial/cancelled的未配对进度原样保留，不自动完成、重试工具或解除busy；已完成会话不能留下未配对请求。

## 实际核心代码

明确事务与资源职责，事务异常回滚并传播：

```python
@contextmanager
def _transaction(self, *, write: bool = False):
    with self._lock:
        if self._closed:
            raise RuntimeError("存储连接已关闭")
        connection = self._connection
        connection.execute("BEGIN IMMEDIATE" if write else "BEGIN")
        try:
            yield connection
            connection.execute("COMMIT")
        except BaseException:
            if connection.in_transaction:
                connection.execute("ROLLBACK")
            raise
```

写入先完成归属、快照、完整集合及状态约束检查；以下两部分位于同一个上述写事务内：

```python
connection.execute(
    "INSERT INTO sessions (session_id, owner_id, snapshot_json) VALUES (?, ?, ?) "
    "ON CONFLICT(session_id) DO UPDATE SET snapshot_json = excluded.snapshot_json",
    (session_id, owner_id, bundle.snapshot.model_dump_json()),
)
connection.executemany(
    "INSERT INTO todos (session_id, todo_id, position, item_json) VALUES (?, ?, ?, ?) "
    "ON CONFLICT(session_id, todo_id) DO UPDATE SET item_json = excluded.item_json",
    todo_rows,
)
```

用户文本通过参数绑定传入，不成为SQL结构。existing todo只更新JSON，不改身份/位置、不删除行；完整集合检查防止调用方只保存普通列表而漏掉逻辑删除项。复用旧快照也不能撤销删除/完成事实。

按可信上下文读回并校验：

```python
def load(self, context: ExecutionContext) -> StoredSession:
    checked = _checked_context(context)
    with self._transaction() as connection:
        row = connection.execute(
            "SELECT * FROM sessions WHERE session_id = ? AND owner_id = ?",
            (str(checked.session_id), str(checked.owner_id)),
        ).fetchone()
        if row is None:
            raise PermissionError("会话不存在或不属于当前用户")
        return self._read(connection, row)
```

_read重新解析JSON、对齐列中ID/owner/session、检查连续顺序及完整模型关系；不会把原JSON当作可信业务对象直接返回。连接每次启用外键，适配器RLock串行执行事务，with适配器在退出时调用close；连接关闭与提交是不同职责。

## 一次具体数据流

1. 现有内存服务创建同owner的A/B会话；A保存聊天历史和completed调用任务，两条同名todo分别完成/逻辑删除，日期保留；B有自己的记录。
2. 显式save分别把A/B快照及各自完整todo集合写入，关闭数据库连接。
3. 新open后load(A)、load(B)得到原消息、TaskState、真实ID、顺序、日期及删除事实；错误owner携带A ID被拒绝。
4. 内存服务改标题不会自动改数据库；只有显式save后才更新，这个边界已测试。自动接入属于S15-b。
5. 临时库触发器让position=1的todo写入失败：session及第一条todo已执行过写入，异常触发回滚；新建场景没有任何记录，更新场景保留上次提交的原值，关闭重开结果相同。

以上使用真实SQLite文件与连接，没有mock数据库、LLM、凭据读取或外发。正式库只做空schema检查，演示数据不混入正式库。

## Python机制、C++类比与取舍

- contextmanager/yield把调用方代码包在BEGIN/COMMIT或ROLLBACK之间，接近C++事务守卫；RLock接近作用域锁，close接近资源释放。连接with本身不能替代对事务与关闭职责的明确管理，依据[Python3.13 sqlite3 §Transaction control](https://docs.python.org/3.13/library/sqlite3.html#transaction-control)与[§Connection context manager](https://docs.python.org/3.13/library/sqlite3.html#how-to-use-the-connection-context-manager)。
- 内存快照是独立值对象，但进程退出就丢失；SQLite提交后关闭重开仍在磁盘。测试实际跨连接恢复，不能用“还有同一个dict”冒充持久化。
- SQLite列保存身份、归属和顺序，JSON复用既有Pydantic数据契约；相比把每种消息/参数都拆表，映射更少，代价是整会话序列化与校验、细字段SQL查询不方便。
- 不选仅写两个JSON文件：跨部分半写更难处理；不选ORM/独立数据库服务：当前单机小步验证无需增加概念和运维。原生Python3.13.16、SQLite3.50.4已实际可用，无新依赖。
- 本步只支持可信调用方提供一致的完整快照，单适配器可串行跨线程访问；没有跨进程合并、版本冲突检测或全局应用单写入者实现。S15-b要在业务锁/提交边界接入，不能先改内存后忽略提交失败。
