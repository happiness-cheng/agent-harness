## 接口与数据契约

- TodoService(sessions)：绑定应用已有SessionStore，持有自己的内存记录。
- add(context, title) -> TodoItem：校验会话归属及标题，创建新记录。
- list_items(context) -> list[TodoItem]：只返回当前session的记录，按插入顺序返回新列表及记录副本。
- TodoItem：id/session_id为UUID，title为严格字符串，status固定pending；严格校验、拒绝额外字段并冻结。
- 标题非空白、最长200字符，保留原文；不截断、不去首尾空格、不按同名合并。这里的字符长度不承诺视觉字形计数。

每次合法add生成新UUID。标题是显示内容，ID才是之后修改/完成/删除要使用的资源标识。同一个标题可以对应多个真实待办；不同session同名也互不影响。当前没有修改、完成、删除、日期或提醒接口。

ExecutionContext由可信入口提供；模型参数不能选择owner/session。check_access只检查会话归属，不代表已检查业务写权限或模式。真实登录仍未实现，进程内应用调用方需要可信。

## 实际核心代码

SessionStore的新入口复用现有归属校验，不复制聊天历史：

```python
def check_access(self, context: ExecutionContext) -> ExecutionContext:
    """仅验证会话归属，不判断业务操作权限或读取聊天历史。"""
    with self._lock:
        session = self._session(context)
        return ExecutionContext(owner_id=session.owner_id, session_id=session.session_id)
```

_session会重新校验严格UUID上下文，并统一拒绝未知session或错误owner。服务每次add/list都检查，不因为曾经访问成功就缓存为长期授权。

todo的实际新增与查询实现为：

```python
def add(self, context: ExecutionContext, title: str) -> TodoItem:
    checked = self._sessions.check_access(context)
    item = TodoItem(id=uuid4(), session_id=checked.session_id, title=title)
    with self._lock:
        self._items.setdefault(checked.session_id, {})[item.id] = item
        return item.model_copy(deep=True)

def list_items(self, context: ExecutionContext) -> list[TodoItem]:
    checked = self._sessions.check_access(context)
    with self._lock:
        return [item.model_copy(deep=True) for item in self._items.get(checked.session_id, {}).values()]
```

内部结构是 `session UUID → todo UUID → TodoItem`。归属先于标题校验；身份无效时不暴露已有记录，也不会写入。TodoItem构造校验成功后才进入写入步骤，非法标题不会留下半条记录。读取使用get而非创建新桶。

RLock保护记录集合的写入和迭代；返回深副本，调用方清空返回列表或替换副本不会污染保存值。TodoItem冻结阻止普通字段赋值，不是防止任意进程内Python代码篡改的安全沙箱。并发新增测试验证40条同名记录均存在且ID不同，不宣称全部并发场景已验收。

## 一次具体的数据流

1. 应用复用SessionStore，创建同一owner的A、B会话，再创建一个长期使用的TodoService。
2. add(A, "写周报")先验证owner/session；构造pending记录与新ID，存入A桶并返回实际记录。
3. 再add(A, "写周报")生成另一个ID，不覆盖或合并第一项。
4. list_items(A)返回两项；list_items(B)为空，即使两个会话属于同一owner。
5. 另一个owner携带A的session ID会被拒绝；A已有记录不变。

这些步骤直接执行真实内存业务服务，没有fake模型或真实LLM。是否记录成功以业务查询结果为准，不根据聊天中“已经新增”的文字判断。

todo是业务记录，S09 TaskState是一次Runtime调用状态。新增todo不会自动开启/完成Runtime任务，也不修改聊天历史。标题里出现“提醒”等字样仍只是标题数据，本步没有调度器或通知能力。

## 方案取舍与C++类比

| 当前方案 | 合理替代方案 | 取舍 |
| --- | --- | --- |
| session分桶，再按ID存记录 | 全局列表或按标题做key | 读取范围明确、同名合法；访问仍须先检查owner |
| 复用SessionStore.check_access | 调snapshot复制全部历史 / 直接访问私有字典 | 身份规则保持单一且不取无关聊天；增加一个窄公共接口 |
| 返回冻结记录副本和新列表 | 返回内部对象供调用方直接修改 | 防隐式写入、便于后续显式update；有复制开销 |
| 直接业务服务 | 立即暴露todo模型工具 | 本步能独立验证业务事实和归属；真实模型选择/模式授权尚未接入 |
| 内存服务实例 | 立即接ORM或通用仓库框架 | 无新依赖、便于读懂；实例销毁或重启会丢数据 |

内部字典可类比C++映射容器，ID是查找键而非标题。Python普通引用可能共享对象，所以显式返回副本，职责更接近返回独立值；类型注解本身不执行校验，实际约束来自Pydantic。with RLock类似作用域锁，保护共享集合，但不构成跨服务的数据库事务。

应用需要复用同一个TodoService实例；重新构造服务会得到空记录，即使绑定相同SessionStore。没有持久化/留存预算、操作重试幂等键或Session生命周期迁移。本步两次add代表两次独立新增，不承诺基础设施重试可直接重复调用而不新增。S15再实现获准后的持久化；S16接模型权限，记录todo不等于具备主动提醒能力。
