## 接口与身份边界

| 接口 / 数据 | 职责 |
| --- | --- |
| ExecutionContext(owner_id, session_id) | 两个严格UUID字段，冻结且拒绝额外字段；由可信应用入口提供 |
| SessionStore.create(owner_id) | 创建独立session UUID，返回上下文 |
| snapshot(context) | 校验归属后，返回深拷贝SessionSnapshot |
| begin(context) | 原子认领本session写入任务，返回running TaskState |
| append(context, task_id, messages) | 校验当前任务归属、消息及配对，整批追加 |
| finish(context, task_id, status=..., run_id=..., error_code=...) | 只允许当前running任务转终态 |
| Runtime.run_session(text, store=..., context=...) | 加载本会话历史、调用模型、保存新增历史及终态 |

TaskState包含task_id/status/run_id/error_code，表示一次Runtime调用。这里只保存当前一次调用的状态，不是业务目标计划、全部任务列表或累计预算。下一次合法调用生成新task_id，历史保留；S16再实现完整目标/模式/授权状态。

owner_id必须来自可信入口识别出的用户身份，不能让外部客户端或模型自行声明。本步没有实现真实登录认证，也不把ExecutionContext称为加密凭证。在进程内运行任意Python代码的调用方仍属于可信应用边界。

每次存储访问都会检查session与owner是否一致；未知session与错误owner统一PermissionError，不返回他人状态。写入还须匹配当前task_id且状态为running，知道别人的task_id也不能越过owner检查。同一owner可以明确访问自己的多个session；模型没有context字段可自行切换身份。

## 实际核心代码

begin在锁内完成归属检查、忙状态检查和认领：

```python
with self._lock:
    session = self._session(context)
    if session.task is not None and session.task.status == "running":
        raise RuntimeError("会话已有运行中的任务")
    if self._pending(session.messages):
        raise RuntimeError("会话历史存在未配对工具请求，不能启动新任务")
    task = TaskState(task_id=uuid4(), status="running")
    session.task = task
    return task.model_copy(deep=True)
```

锁只覆盖短存储操作，不覆盖模型和工具执行。不同session不会因另一个session有running任务而被拒绝。同一store有RLock保护操作；竞争认领测试用两个线程和Barrier启动，实际只有一个任务成功。该测试证明存储认领边界，不证明模型适配器或trace的多线程执行安全。

写入先校验全部消息，再检查整个候选历史，最后一次追加：

```python
with self._lock:
    session = self._active(context, task_id)
    validated = []
    for message in messages:
        if not isinstance(message, Message):
            raise TypeError("历史必须由 Message 组成")
        validated.append(Message.model_validate(message.model_dump(warnings="error")))
    self._pending(session.messages + validated)
    session.messages.extend(validated)
```

Message可能已被可信代码原地改坏，因此不能直接存原对象。重新导出/解析也会切断嵌套工具参数的可变引用；snapshot再深拷贝一次，调用者修改输入或读取快照均不会写回存储。SessionSnapshot本身允许修改，它是脱离存储的副本；只有显式append/finish才写入。

_pending按历史顺序检查：工具结果必须属于当前未完成请求，结果不能重复；未配齐结果前不能进入下一条user/assistant等非tool消息。允许历史末尾暂时存在pending请求，以便保留失败时的真实进度，但completed不能带pending，新begin也会拒绝。这不是任意聊天语义或全部业务完成校验。

Runtime使用如下实际流程加载历史并关联trace：

```python
task = store.begin(context)
messages = store.snapshot(context).messages
original_length = len(messages)
messages.append(Message(role="user", content=text))
run_id = uuid4()
trace_context = TraceContext(session_id=context.session_id, task_id=task.task_id)
try:
    result = self._run_traced(text, trace_context, run_id, messages)
except BaseException as error:
    interrupted = not isinstance(error, Exception)
    store.append(context, task.task_id, messages[original_length:])
    store.finish(
        context, task.task_id, status="cancelled" if interrupted else "failed",
        run_id=run_id, error_code="interrupted" if interrupted else "unexpected_error",
    )
    raise
store.append(context, task.task_id, messages[original_length:])
store.finish(context, task.task_id, status=result.status, run_id=run_id, error_code=result.error_code)
return result
```

输入在begin前校验；begin在模型调用和trace开始前检查owner/session，因此错误归属不会发起模型调用。_run_traced复用S08观测和原循环，普通run仍是无会话的独立调用。

每轮模型收到历史的深快照。正常终态会保存已有assistant正文；工具分支保存请求和实际结果。仅提交messages中本次新增的部分，避免把旧历史再追加一遍。存储在调用结束或异常传播前提交本次历史；运行中的snapshot显示上次历史及running任务，并不是逐条实时流。

## 一次具体数据流

同一owner创建A、B两个会话，脚本模型按顺序响应：

1. A输入“A第一次”，保存user及“A第一次回答”，A任务completed。
2. B输入“B第一次”，模型只看到B输入，保存B两条消息。
3. A输入“A计算”，模型看到A之前两条消息及新输入，不含B内容。
4. A请求calculator计算0.1+0.2，实际返回JSON封装的0.3；请求、对应tool结果和最终assistant回答都只存入A。
5. B再次追问时只加载B历史；A/B的当前task_id不同，run_id分别匹配各次返回结果。trace的session/task标签来自可信存储上下文。

测试模型决策是脚本，不证明真实LLM记忆或理解正确；calculator确实执行了本地Decimal计算。

## 失败和历史完整性

| 情况 | 保存 / 拒绝行为 |
| --- | --- |
| 未知或越权session、错误task | 抛PermissionError，模型不调用，其他状态不改 |
| 同session已有running任务 | 拒绝第二次begin；其他session仍可认领 |
| 正常模型错误/截断/拒绝 | 保存user及已有正文，状态按RunResult记录 |
| 模型中断 | 保存user和cancelled/interrupted，继续传播中断 |
| 部分工具成功后handler失败 | 保留整条assistant请求及已完成tool结果，状态failed；不重放 |
| 存在未配对工具请求 | 可以保存failed/partial/cancelled，但不能completed或直接启动新任务 |
| 旧任务或已结束任务再写 | 拒绝，不污染新任务 |
| 同批消息中途校验失败 | 整批不追加，不留下有效前缀 |

length/refusal/error中的未执行工具请求不会当作已执行历史写入；只保存已有正文，完整原响应仍在RunResult.response。无工具能力时的工具响应也不虚构执行消息。本步消息历史是模型可用的对话记录，不是原始provider响应档案。

当handler失败导致pending请求时，本步选择阻止新任务；尚无自动核对未知副作用、补结果或恢复的公开接口。既不丢掉请求，也不把失败结果伪装成功。后续恢复策略需要按实际工具和任务状态实现。只因最后一次正常回答而completed，也不证明复杂业务目标完成。

append的整批校验与finish是两次存储操作，不是持久事务。存储本身写入失败、进程强杀、重启恢复没有保证；当前全部数据在内存中，S15才实现获准后的持久化。模型/工具执行期间的消息也未实时持久保存。

## Python机制、C++类比与取舍

- 实例内dict类似由SessionStore拥有的C++映射容器，owner/session/task明确归属；没有全局共用messages。
- Python普通赋值共享对象引用；深快照更接近返回值副本，而非暴露C++可变引用。Pydantic冻结只阻止常规赋值，不是防止任意进程内代码篡改的沙箱。
- with RLock类似用作用域锁保护共享状态；“检查running再设置running”必须在同一临界区，不能靠两个分开的检查保证唯一写入者。

| 当前方案 | 合理替代方案 | 取舍 |
| --- | --- | --- |
| 显式store/context | 全局当前session或从模型参数选择owner | 数据流和访问边界可检查；参数更多 |
| 深快照再显式写入 | 直接返回内部Session对象 | 避免隐式污染；复制有开销 |
| 存储锁内认领当前任务 | 仅靠提示词不重复启动 | 竞争认领可验证；不自动提供队列/取消调度 |
| 每次检查完整候选历史配对 | 只追加最后一条而不校验 | 不容易接受错配或漏结果；历史增长会增加检查成本，压缩/预算尚未实现 |
| 内存当前任务状态 | 立即上数据库或完整任务系统 | 本步容易阅读与测试；重启丢失，不保留所有任务状态档案 |

真实认证、Plan/Build、todo、队列、通用预算、主动超时和上下文压缩仍未实现。不同session交替调用已验收，真正并发运行共享Runtime/模型/trace未验收。
