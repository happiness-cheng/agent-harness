## 目标与文件范围

用户在 S04 交付后回复“同意”，本步只完成输入 → 模型直接回答 → 返回终态。

核心文件为 [runtime.py](../../src/min_agent/runtime.py)、[脚本化模型](../../tests/fakes/model.py) 和 [行为测试](../../tests/unit/test_runtime_reply.py)。另加 [tests 包标记](../../tests/__init__.py) 与 [fakes 包标记](../../tests/fakes/__init__.py)，使测试替身能可靠复用；没有新依赖。既有五个源码模块与 S04 wheel 逐字比较一致。

没有执行工具、构造真实 API 请求或读取凭据；没有新增会话存储、重试、预算、后台任务和 trace。这里是未来循环的入口与终态切片，还不是完整 Agent。

## 公共接口

```python
class Model(Protocol):
    def generate(self, messages: list[Message]) -> ModelResponse: ...

@dataclass(frozen=True)
class RunResult:
    status: Literal["completed", "partial", "failed"]
    response: ModelResponse | None = None
    error_code: str | None = None
```

`Runtime(model).run(text)` 接收一条非空白字符串。模型只需提供 `generate`，不用继承具体基类；Runtime 不知道服务商、密钥或网络地址。返回的 `response` 保留正文、工具请求与模型提供的公开推理摘要，不生成隐藏思维链。

`completed` 在本步只表示有效 `stop` 直接回答正常返回，不验证答案事实正确，也不证明复杂用户任务已经完成。`partial` 表示保留了输出或请求，但当前路径没有完成；`failed` 表示拒绝、模型错误、调用异常或响应契约错误。后续业务终态不能直接套用“收到 stop 就任务完成”。

## 核心控制流

以下为实际 `run` 实现：

```python
def run(self, text: str) -> RunResult:
    if not isinstance(text, str):
        raise TypeError("输入必须是字符串")
    if not text.strip():
        raise ValueError("输入不能为空白")
    messages = [Message(role="user", content=text)]
    try:
        response = self._model.generate(messages)
    except Exception:
        # 异常正文可能含请求或凭据；结构化诊断在 S08 接入。
        return RunResult(status="failed", error_code="model_call_failed")

    if not isinstance(response, ModelResponse):
        return RunResult(status="failed", error_code="invalid_model_response")
    try:
        # 先转回数据再解析，重新校验嵌套字段并切断可变引用。
        response = ModelResponse.model_validate(response.model_dump(warnings="error"))
    except (ValueError, TypeError):
        return RunResult(status="failed", error_code="invalid_model_response")

    match response.finish_reason:
        case "stop":
            return RunResult(status="completed", response=response)
        case "length":
            return RunResult(status="partial", response=response, error_code="output_limit")
        case "tool_calls":
            return RunResult(
                status="partial", response=response, error_code="tool_execution_not_supported"
            )
        case "refusal":
            return RunResult(status="failed", response=response, error_code="model_refusal")
        case _:
            return RunResult(status="failed", response=response, error_code="model_error")
```

输入检查只用 `strip()` 判断空白，传给模型的仍是原文。每次调用都新建消息列表，不把上次内容存到 Runtime 实例，因此目前两次 run 是两个独立请求，不提供持续对话。

`try` 只包模型调用；模型抛出的普通异常变成固定错误码，不返回或打印其正文，也不重试。`KeyboardInterrupt` 等 `BaseException` 不会被吞掉。此时没有结构化诊断，适配器编程错误也会被归入调用失败，这是当前的明确限制；S08 再补可定位且脱敏的事件。

返回类型正确仍不足够：S02 对象允许修改，原先有效的 `content` 或嵌套工具参数可能已经变坏。先导出数据、再解析会重新校验并构造独立快照。`warnings="error"` 也会拒绝被修改成不符类型而无法按契约序列化的字段。直接 `model_validate(response)` 不能作为这里重新校验嵌套数据的保证。

`match` 按项目内部结束原因选择结果：

| 模型结束原因 | Runtime状态 | error_code |
| --- | --- | --- |
| stop | completed | None |
| length | partial | output_limit |
| tool_calls | partial | tool_execution_not_supported |
| refusal | failed | model_refusal |
| error | failed | model_error |

正常化后的响应只有这五种结束原因，其他值在重新解析时被拒绝。`length` 即使带有工具请求也只保留数据，本步没有执行路径；模型写出正文不改变它的截断状态。

## 一次具体数据流

测试输入为 `"  请介绍自己。  "`：

1. `run` 验证输入，创建 `Message(role="user", content="  请介绍自己。  ")`。
2. 通过模型协议调用一次 `generate([message])`。
3. fake 记录消息快照，并取出预设的 `ModelResponse(finish_reason="stop", content="  你好，这是回答。  ")`。
4. Runtime 重新校验并复制响应，匹配到 stop，返回 completed；输入和输出的首尾空格均保留。
5. 测试检查返回值及 `model.calls` 的完整消息列表，保证没有漏传输入、重复调用或偷偷追加其他历史。

截断示例走同样的一次调用，但输出 `length/尚未结束` 得到 `partial/output_limit`。这说明“模型结束生成”与“Runtime报告正常完成”是两个不同判断。

## fake 与 Python / C++ 类比

脚本化 fake 使用 `deque` 保存预设响应或异常，每次 `popleft()` 取下一项；没有根据输入关键词决定回答。记录消息时深拷贝，避免后续对象修改污染观察结果。脚本耗尽会抛 AssertionError，没有兜底答案。Runtime 会把该普通异常归为调用失败，所以测试还检查调用记录，不能只检查最终状态。

这类 fake 验证的是 Runtime 对协议的处理，不能证明真实模型会选 calculator、理解用户意图，或真实账号可用。

`Protocol` 可类比 C++ 的接口约定或模板约束：调用方关心 generate 的签名。但 Python 这里不要求继承、不自动提供编译期保证；项目未配置静态类型检查器。实际边界依靠运行时输入检查和 Pydantic 响应校验。

`RunResult` 类似保存状态与响应的 struct。`frozen=True` 禁止直接替换顶层字段，内部 `ModelResponse` 仍可变；它不是深层不可变对象。Python 普通赋值共享对象引用，所以需要显式快照，不能套用 C++ 值类型复制的直觉。调用者后续修改自己的响应内容不会回头改适配器对象，但状态不会随这种修改重新计算。

## 方案与取舍

| 当前选择 | 合理替代方案 | 本步取舍 |
| --- | --- | --- |
| 同步 generate 与明确的一次调用 | async generate / 完整 while 循环 | 控制流易读、无新依赖；调用会阻塞，且没有主动超时或取消机制，后续接服务时再评估 |
| 协议注入模型 | Runtime 内直接创建具体 API 客户端 | 单测无需网络/密钥；多一层接口，但模型来源和控制流职责清楚 |
| 预设脚本 fake | 关键词分支 fake / 每次真 API | 响应顺序稳定且可复现；无法证明模型推理能力，真实验收留到 S17 |
| 结构化状态与固定错误码 | 一律返回字符串或直接传播所有异常 | 能保留部分输出并避免异常正文泄漏；调用者需检查状态，诊断能力暂有限 |
| 重新解析响应快照 | 信任原对象或仅做浅复制 | 嵌套边界可验证；多一次小规模序列化/校验开销，未做性能基准 |

没有为未来所有终态、权限、会话或工具执行预建框架；当前结果类为可信 Runtime 内部构造，dataclass 类型注解本身不提供运行时参数校验。
