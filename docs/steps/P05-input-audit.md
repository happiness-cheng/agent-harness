## 检查方法及能力边界

本轮使用systematic-debugging方法：先核对事实，再给可验证假设，不因怀疑工具诱导就立即改工具。

依据P04报告中的提示原文、应用状态、问题和工具Schema，调用当前DeepSeek适配器的纯请求构造方法重建12个JSON请求。没有初始化HTTP客户端、读取凭据或联网。此为离线重建，不是历史HTTP抓包，不能证明提供商内部如何解释输入。

同时静态核对主应用、待办、提醒和计算工具的注册代码；检查评估脚本的直接模型调用链及上下文入口。静态工具目录不是本轮运行时采样的真实会话目录，不冒充线上观测。

## 已确认的事实

### 1. 当前本地构造链没有漏掉用户问题

12个重建请求均有3条消息：system完整提示、user角色的application_state、user角色的合成问题。提示和问题与报告逐字一致，全部5个工具定义被保留。用于人工评分的expectation没有发给模型。

因此，没有发现“脚本只发了会话状态、没发用户正文”的构造错误。模型说“这条消息只有会话状态”与本地可重建输入不符，不能反过来拿模型的话当成请求丢失的证据。

### 2. 这组评估没有经过压缩或记忆召回

评估脚本直接调用DeepSeekResponsesModel.generate，再由build_input构造请求；没有进入主应用的ManagedModel或ContextManager.prepare。因此，P04这批回复不能归因于应用压缩丢掉了问题。此结论仅针对该评估入口，不是对真实应用所有路径的无损保证。

输入没有历史会话、记忆查询结果、Checkpoint源码或项目知识材料。学习进度只来自合成用户问题中的自述，不能据此评价真实记忆召回。

### 3. 评估工具集明显小于主应用

实验固定提供5个工具：propose_goal、reminder_add、reminder_cancel、reminder_list、reminder_update。

当前注册代码可静态确认17个固定工具。实验缺少12个：calculator、todo_add、todo_complete、todo_delete、todo_list、todo_update、read_artifact、read_memory_source、read_session_state、read_skill、recall_memory、research。

两版使用同一受限工具集，仍可以做该条件下的首轮提示对比；但不能直接推断完整主应用的能力，也不能推断给了真实记忆或源码后仍会这样回答。

### 4. 概念错误需要独立核对，不应被语气评价掩盖

新旧学习计划均将检查点主要描述成暂停或审批节点。项目实际Checkpoint记录了运行原因、预算、历史范围、工具结果引用等，CheckpointRecord还保存归属、目标及历史哈希；它们服务恢复绑定，不等同于“必须向用户确认的一个节点”。本批模型没有拿到这些定义，不能只因计划看起来条理清晰就判定其教学内容正确。

这证明知识材料没有提供，也证明回答存在错误；尚未证明“补上材料就一定修好”。

## 可验证假设与下一步

| 假设 | 如果成立，应观察到什么 | 当前结论 |
| --- | --- | --- |
| 工具暴露使回答偏向提醒业务 | 同一提示、问题和状态，仅移除提醒类工具后，额外提醒建议减少 | 未验证因果；当前只确认目录以提醒为主 |
| 缺少必要知识造成检查点概念错误 | 保持其他输入不变，补充真实定义后，相关解释更准确 | 未验证因果；当前只确认没有材料和有错误 |
| 过多主动分析规则导致扩写 | 固定输入与工具，简化主动分析要求后，未核对的推断和冗长减少 | P04出现相应现象，每场景仅一次，仍不足以证明稳定因果 |
| 请求构造丢掉用户正文 | 重建body中缺少或改变合成问题 | 当前构造路径不支持该假设，12/12原样保留 |
| 应用压缩丢掉重要信息 | 评估经过压缩入口且可见投影变化 | 本评估没有经过该入口，不支持用压缩解释本批结果 |

建议先做两个独立小实验：其一只改变工具暴露，其二只改变知识材料。固定同一提示和合成问题，分别观察不必要建议、事实准确性、澄清必要性和成本；不要同时换提示、知识、工具再归因。正式判断需多次与多轮结果，不把单条回答当总体能力。

上述是实验设计，尚未执行。没有追加请求预算，也没有把有限工具集直接改成生产工具裁剪策略。
