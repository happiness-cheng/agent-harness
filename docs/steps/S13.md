TodoItem增加严格布尔字段deleted，默认False；与pending/completed独立，删除保留原标题、ID、归属和完成状态。`delete(context, item_id: UUID) -> TodoDeletionResult`返回冻结的item及changed：首次标记True/changed=True；再次返回已删记录副本/changed=False。未知ID是KeyError，不自动生成已删记录。

## 实际核心代码

删除方法只查当前会话，查找、判断及标记在同一把锁内：

```python
def delete(self, context: ExecutionContext, item_id: UUID) -> TodoDeletionResult:
    checked = self._sessions.check_access(context)
    if not isinstance(item_id, UUID):
        raise TypeError("item_id 必须是 UUID")
    with self._lock:
        items = self._items.get(checked.session_id, {})
        current = items.get(item_id)
        if current is None:
            raise KeyError("当前会话中未找到todo")
        if current.deleted:
            return TodoDeletionResult(item=current.model_copy(deep=True), changed=False)
        deleted = TodoItem.model_validate({**current.model_dump(), "deleted": True})
        items[item_id] = deleted
        return TodoDeletionResult(item=deleted.model_copy(deep=True), changed=True)
```

普通查询统一过滤已删除项：

```python
def list_items(self, context: ExecutionContext) -> list[TodoItem]:
    checked = self._sessions.check_access(context)
    with self._lock:
        return [
            item.model_copy(deep=True)
            for item in self._items.get(checked.session_id, {}).values()
            if not item.deleted
        ]
```

update与complete的查找失败条件同步变为`current is None or current.deleted`，统一KeyError。特别是complete必须先检查deleted，再进入“已完成则直接返回”的分支，避免已完成且已删除项绕过检查。update也先检查记录，再验证新标题；对已删除记录传空标题仍是未找到，不产生半写入。

每次访问（包括重复delete）先验证owner/session，错误owner或不存在会话是PermissionError，非法UUID参数是TypeError。当前session中的未知ID与其他session ID统一未找到，不全局搜索、不回显ID，不泄露别处是否存在。Python函数参数绑定错误发生在方法体之前，不承诺这类错误也先校验归属。

首次删除只覆盖deleted并完整重新校验TodoItem，成功后才替换。已删除分支不再写入。所有返回值为冻结副本，旧快照仍保留之前的数据；冻结不等于进程内恶意代码的安全沙箱。

## 一次具体的数据流

1. A新增两条“写周报”，ID不同；B也有自己的待办。先把A第一条完成，其状态为completed。
2. delete(A, 第一条ID)验证归属、在A桶定位，保存deleted=True，原标题和completed状态保留，changed=True。
3. list_items(A)仅剩第二条；B不变。再次delete第一条返回相同业务记录、changed=False，不重写。
4. 对已删除ID执行update或complete均拒绝；未知/外session ID及错误owner也拒绝。查询和重复删除确认没有意外修改。
5. A再次新增“写周报”获得新ID且deleted=False；旧ID仍已删除。会话历史及正在running的TaskState保持不变，业务删除不等于结束Runtime调用任务。

以上真实内存业务服务流程已用隔离解释器手动运行，退出0；无fake模型、真实LLM、凭据读取或外发。

## Python机制与C++类比

- status与deleted相当于C++值对象中的完成枚举和独立bool；completed且deleted=True表示“删除前已完成”，两个维度各有含义。Python注解不提供自动静态保证，Pydantic严格构造/重新校验负责运行时约束。
- 字典展开复制当前完整字段，仅覆盖deleted，再model_validate；不使用跳过校验的model_copy(update=...)写内部状态。返回时深副本类似返回独立值对象，不共享可变存储入口。
- `with self._lock`接近RAII作用域锁，不依赖Python析构时机。判断已删及首次标记在同一临界区，所以并发同ID只有一个changed=True。
- 列表推导式在创建新返回列表时筛选deleted=False；过滤的是展示/业务访问范围，不会物理清除被过滤的记录。存活项仍按原字典插入顺序返回。

## 方案取舍与限制

选择逻辑删除，是用户确认的数据保留策略；可保留原记录事实、区分已删和从未存在，并明确返回重复无变化。代价是每个相关读取/写入口都要处理deleted；已删内容持续占用内存，也会增加后续遍历成本。测试特别覆盖修改/完成入口，不能只过滤列表就声称删除完成。

物理删除的合理优势是结构简单、无需保留已删记录；代价是无法返回该原记录，恢复需要额外历史。另一种方案把status改成deleted会减少一个字段，却覆盖原pending/completed事实；本步采用独立标记，避免丢失完成状态。没有为去重复代码而引入通用状态机或仓库框架。

逻辑删除不是隐私擦除；原内容仍保存在当前服务实例内，先前已返回的快照也不会被追溯修改。本步没有恢复接口、保留期限、自动清理、审计历史、数据库持久化或跨进程保证。不能把“保留了原记录”说成已具备可用恢复功能。

这里的幂等只针对内存业务状态，首次与重复响应的changed可以不同。锁与标记不保证崩溃恢复、基础设施重试或外部通知恰好一次；后续S15/S25/S40再分别处理存储、恢复及提醒联动。本步没有提醒能力，未声称删除已取消通知。
