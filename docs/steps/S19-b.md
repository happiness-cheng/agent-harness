## ID、归属及接口

| 字段/对象 | 意义 |
| --- | --- |
| budget_id | 可信入口明确创建的一项预算任务ID，跨执行片段/进程保持 |
| owner_id/session_id | 预算必须属于当前可信身份上下文与会话 |
| active_budget_id | 当前会话允许使用哪项持久预算；新任务/切回旧任务都需可信入口明确操作 |
| SessionStore.TaskState.task_id | 每次begin的新执行ID，不作为累计预算ID |
| GoalProposal.proposal_id | 目标提案版本，不用于清零累计预算 |
| revision | 存储并发比较版本，不是调用次数；新片段或切换也会增加 |
| limits/usage/segments | 固定总限额、累计用途计数、全部片段/子片段限额与消耗 |

可信接线示例（上下文/存储/模型须已由可信入口建立，不是完整启动脚本）：

```python
budgets = SessionBudgets(store)
budget_id = budgets.create(context, BudgetLimits(model_calls=2, tool_calls=1))
ledger = budgets.open(context, budget_id)
segment = ledger.start_segment(BudgetLimits(model_calls=1, tool_calls=1))
runtime = Runtime(model, tools, budget=segment)
result = runtime.run_session("计算", store=store, context=context)
# 正常片段结束后重启：新SessionStore从同一SQLite加载，再open原budget_id。
# 新片段只更新片段额度，原任务累计及固定总限额保留。
```

create表示明确的新任务并选择为活动预算；select只切换已有任务、保留原限额和消耗；open恢复，不在缺失/损坏时自动新建。模型工具中没有预算管理接口，不能用自然语言“同意”直接生成新任务或扩大额度。预算本身不授予Build/业务写权限，原TaskController仍执行。

活动持久预算会话必须使用当前SessionBudgets恢复的唯一账本：省略budget、换新内存账本、复制正确binding ID、错绑owner/session/SessionStore，均在begin/模型调用前拒绝。仅比较UUID不够，当前存储缓存中的对象身份也须匹配。旧无活动预算会话保留旧兼容行为，不声称所有入口自动启用。

## 核心代码与提交顺序

SessionBudgets.open恢复账本时安装的实际提交回调：

```python
def persist(state):
    check_context(context, self._sessions)
    current = self._sessions.snapshot(context).budgets[budget_id]
    if current.state != previous_state[0]:
        raise ValueError("预算句柄状态已过期")
    candidate = BudgetRecord(**{
        **current.model_dump(), "revision": current.revision + 1, "state": state,
    })
    self._sessions.set_budget_record(context, candidate, expected_revision=current.revision)
    previous_state[0] = state
```

previous_state用一个可变容器保留闭包中的上次已提交状态，便于和当前会话比较；类似C++闭包持有共享状态引用，但Python作用域/对象引用不等同于C++值捕获。它不是数据库事实，数据库的事务版本检查才是最后写入门。

具体数据流：Runtime请求消费→任务/所有父片段检查→锁内暂记候选计数→回调验证绑定与旧状态→SessionStore构造新记录→SQLite BEGIN IMMEDIATE读取真实旧revision、校验其余预算不变→写完整快照并COMMIT→发布内存记录→consume返回→才调用模型/handler。

持久账本共用SessionStore的RLock，不另造ledger→session与业务session→ledger的交叉锁顺序。锁只覆盖计数/存储提交，释放后才执行外部模型或业务handler。新片段创建也先保存，不会重启后恢复为未花过的片段；恢复过程本身不重扣或回调保存。

校验范围包含：严格非负整数/版本类型、总额不越限、用途分项合计、父节点存在/无环、子消耗不超过上级、所有根片段合计等于任务累计。更新不能删旧片段、改旧限额/父级/归属或降低任何分项。损坏数据拒绝启动，不能降级空账本。

## 为什么候选相同仍要检查版本

假设两个独立存储实例都读到revision=1、模型消耗0，都计算候选revision=2、消耗1。如果第二个只看到“新值已经等于候选”就放行，会执行两次调用却只记1次。现在预算写入显式携带expected revision；第二个即使候选完全相同，也因实际版本已2而失败。普通消息/todo保存则必须保持全部预算和活动ID完全不变，旧快照也不能抹掉新消耗。

这是比较并提交，类似C++里持有版本号做compare-and-swap；这里由SQLite写事务串行读取/更新，并不是靠Python对象比较就保证跨进程原子性。冲突旧实例停止并要求重新加载，不自动重试/合并；其他普通业务并发仍维持既有单活动SessionStore边界。

## 失败、恢复与已知限制

存储提交失败时，当前模型/工具不启动，Runtime返回failed/budget_persistence_failed；工具请求配齐not_started结果，trace仅固定分类，不回显SQL异常。候选内存计数回滚，但这个账本句柄同时停用；需要从SQLite重新建立SessionStore再open，不能只是新建片段或SessionBudgets包装器。

停用很关键：提交可能已经成功，只是确认返回时出错。若仅回滚内存后继续消费，会把已花额度再次放行。测试用合成回调模拟“提交后抛错”，证明旧句柄不再消费，再从已提交快照恢复；它不是实际断电/存储硬件故障测试。SQLite真实ABORT触发器另外验证已知回滚时内存/盘面仍保留前次状态。

预扣意味着“获准尝试”，不是“调用一定已发出/工具一定已执行”。崩溃在提交后、派发前可能保守占用额度，不自动退还。若运行中进程突然退出，已有TaskState.running/未知业务结果不会被本步自动清空或重放；完整检查点与未知结果核对/幂等留S20/S25。只证明正常partial结束片段之后的跨进程续跑，并不承诺exactly-once。

复用完整快照简化了归属和事务一致性，但每次预扣都会带来SQL写入及快照校验开销。当前小规模单机流程优先正确性；不顺便加入日志表、分布式锁或自动合并。固定总限额不因select/新片段改变；新增预算任务须由可信入口明确决定，不是模型自动续费机制。token窗口、usage/精确费用与模型取消仍不是这组调用次数指标。
