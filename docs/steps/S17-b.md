实际核心代码（openai_protocol.py中的_state_output，调用点位于响应解析及历史编码）：

```python
def _state_output(output: list, provider: str) -> list:
    result = deepcopy(output)
    if provider == "deepseek.responses":
        for item in result:
            if item["type"] == "reasoning":
                # 仅保留已验证的原生内容，丢弃不支持的兼容元数据。
                item.pop("summary", None)
                item.pop("encrypted_content", None)
    return result
```

数据流实例：DeepSeek返回原生reasoning及calculator函数调用→验证content→复制并去掉不支持的元数据→Runtime根据真实call_id执行本地calculator→回传字符串0.3的工具结果及保留的原生状态→模型返回stop。Python的deepcopy复制嵌套列表/字典，pop只改变副本；类似C++先复制值对象再删字段，但Python普通赋值会共享对象引用，不能将两者等同。原生reasoning内容依然是明文协议状态，不能当作模型摘要展示。

选择保留受支持内容、丢弃附加字段，而非整项丢弃reasoning，避免丢失续传状态；也未改成无条件接受所有content，以保留协议边界。代价是提供商专属兼容逻辑仍须维护，新字段不会自动成为支持能力；本次有限验收不证明所有响应稳定。相比复制整套HTTP客户端，该修复复用现有协议入口，没有新依赖或额外模型调用。

## 状态、数据流与隐私边界

固定用户输入 → DeepSeekSettings仅取指定文件deepseek_api_key → DeepSeek请求构建 → 固定官方HTTPS → 按deepseek.responses投影 → Runtime处理回答或真实工具 → function_call_output按call_id回传 → 再次生成。

ProviderState记录请求model、响应model与受支持的原生output；最新修复会先验证并去掉DeepSeek不支持的附加summary/encrypted_content，其余原生内容保留。编码前重新校验消息、工具配对、provider/model与可见内容/调用投影；DeepSeek状态不能给OpenAI，OpenAI密文也不能给DeepSeek。DeepSeek允许省略item.id，不捏造远端ID；工具关联使用真实call_id。

DeepSeek不提供OpenAI式加密状态/摘要。本地接受reasoning_text原生内容作为协议往返数据，不把它拼进回答或reasoning_summary，不自行伪造摘要。上一轮解析器会直接拒绝非空summary/encrypted_content；最新兼容规则见上方补记。未知远端工具类型和未完成条目仍拒绝；上一轮前两次实测的具体校验点没有取得，不追溯改写其原因。

重要的存储区别：DeepSeek原生reasoning内容是明文。provider_state虽在repr中隐藏，若应用把消息写入既有SQLite JSON，明文仍会持久化；这不是磁盘加密。本步正式库不写，测试只用合成占位状态/临时库，真实烟测仅内存处理。重启测试重建SessionStore和新适配器，确认不依赖旧响应缓存。
