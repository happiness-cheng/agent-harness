# 按当前模型能力决定上下文窗口

用户明确要求：上下文预算不得固定写死，应依据当前模型能力。沿已确认的修复方向直接执行，不修改Memory策略、数据库、权限或调用费用门禁，不运行付费生成。采用系统化调试、测试先行与执行工作流；本计划兼作小任务进度文件，不覆盖用户旧计划，不提交/推送。

## 已核对的依据与取舍

- DeepSeek官方 `GET /models` 的 Schema 定义 `context_window`（输入输出Token总容量）、`max_output_tokens`；https://api-docs.deepseek.com/api/list-models/ §Responses。
- 当前 `ContextManager` 固定32768，并以内部Message序列化字节估算；可见文本与原生状态被同时计入。真实两问样本搜索后、动态状态加入前就达到34557（含预留），被本地门禁阻断，不是服务端证实超窗。
- 推荐：Provider读取并缓存能力元数据；真实Runtime/压缩/Skill/研究子循环共享该窗口。未知/损坏元数据明确报错，不回退猜测32K。运行器不抓网页或凭模型自述决定容量。
- 不采用：将32K替换成硬编码1M；关闭窗口门禁；为了通过删掉协议续传状态。
- 输出请求上限仍是用户/应用的生成配置，不能超过模型最大输出。调用次数和工具预算仍是独立资源限制。
- 按真实Provider请求体估算，避免重复计算内部保存字段；暂不引入新Tokenizer依赖，UTF-8字节仍明确标记为保守估计而非精确Token。
- Demo/无Provider脚本模型只有明确标注的本地测试窗口；这不作为真实型号的容量。已有显式小窗口测试保留。

## 固定验收

1. 模型metadata窗口变化时相同请求的准入结果随之改变，不依赖特定型号数字。
2. GET只发送认证和模型元数据请求，不带聊天、Memory或工具内容；不占生成request_count，一实例缓存一次。
3. 元数据缺失、类型非法、型号不匹配、网络错误不回退32K，不生成。
4. 超过模型真实上限仍暂停；显式本地限制只能收窄，输出预留仍计算。
5. 使用实际DeepSeek协议Mock，在完整Harness中重放“自我介绍→搜索空Memory→最终回答”，保留原生状态、无需无谓压缩并完成回答。
6. 主循环、压缩、Skill与研究循环使用同源窗口；既有Memory安全、权限、调用预算回归保留。
