## 接口及预算含义

BudgetLimits(model_calls,tool_calls)必须显式提供两个非负整数，0允许，bool/浮点/字符串不接受。没有未经讨论的统一调用阈值：演示中的1、2仅用于验证边界。预算由可信应用入口持有，不接受模型提供的owner/session/预算参数来扩大额度。

1. BudgetLedger(total_limits)持有一个任务累计额度；start_segment(limits,purpose='main')创建本次执行片段，不清空累计。
2. segment.consume('model_calls'/'tool_calls')先检查片段全部父级及任务总额，再同时扣除；拒绝时任何层都不扣。
3. segment.child(limits,purpose=...)仍受父级与任务限制。子片段不提前预占额度，逐次消费，不保证每个子片段都能用满自己的标称上限。
4. ledger.usage/segment.usage返回独立快照，含model_calls、tool_calls及by_purpose；修改快照字典不会改实时账本。
5. 用途限定main/repair/retry/research/compaction。Runtime参数修正后的派发归入repair；其他用途由可信入口明确选择，不因记了research/compaction就声称研究Agent或压缩已实现。

| 指标 | 本步如何处理 | 不可混淆的概念 |
| --- | --- | --- |
| 用户对话轮次 | 可另外按会话历史的user消息统计 | 一个用户输入可能触发多次模型生成；不从model_calls推导 |
| 模型派发尝试 | Runtime预算门放行一次记一次，异常不退还 | 包括本地准备/适配器验证失败的保守扣除，不一定发出HTTP |
| 工具派发尝试 | 一次registry.execute前记一次；Schema错误/权限拒绝仍计入 | 不等于handler实际执行或成功写入次数 |
| 实际HTTP尝试 | 仍由原client.request_count统计及限制 | 新任务账本与客户端门同时生效，不自动提高客户端限额 |
| 当前上下文窗口 | 本步不估算，留S30 | 单次输入/输出预留，与累计调用消耗不同 |
| 计费token/费用 | 没有实际usage/定价计量，不虚构 | 调用数不是token；已发远端请求可能继续处理/计费 |

原适配器的max_output_tokens、超时、TLS和固定端点仍执行。此步只提供调用次数硬上限，不声称精确货币硬上限、HTTP取消或计费退款。

## 核心代码与具体数据流

实际[BudgetSegment.consume](../../src/min_agent/budget.py)（按函数名定位；以下保留S19-a当时核心片段）：

```python
with self._ledger._lock:
    nodes, node = [], self
    while node is not None:
        nodes.append(node)
        node = node._parent
    if self._ledger._counts[resource] >= getattr(self._ledger._limits, resource):
        raise BudgetExceeded("task", resource)
    for node in nodes:
        if node._counts[resource] >= getattr(node._limits, resource):
            raise BudgetExceeded("segment", resource)
    # 全部检查通过才扣除；不因异常或子调用而退还/重复扣累计额度。
    for owner in [self._ledger, *nodes]:
        _increment(owner, resource, purpose)
```

RLock覆盖所有层的检查与扣除，其他线程不能在检查后插入另一次消费；子片段、父片段与累计各记一次，累计不会按层数重复加。类似C++共享预算对象配合锁，不能把“先读remaining再异步执行”当作原子许可。Pydantic负责边界校验/快照值；Python类型注解本身不代替检查，frozen也不等于所有嵌套对象不可修改，所以快照与原始限额均隔离。

具体例子：任务累计允许模型2/工具1，首片段模型1/工具1。模型请求calculator→模型额度1次、真实calculator执行1次，结果写入会话→准备下一次模型调用时片段模型额度耗尽，返回partial/budget_exhausted，模型不启动。可信入口明确分配第二片段模型1/工具0，复用同一账本和会话历史→模型读取已有真实工具结果并回答，累计模型2/工具1，calculator仍只执行过1次。第三片段即使宣称模型10，也不能绕过任务累计2。

公共接线片段如下（model/tools/store/context须已由可信入口建立；不是独立启动脚本）：

```python
ledger = BudgetLedger(BudgetLimits(model_calls=2, tool_calls=1))
first = ledger.start_segment(BudgetLimits(model_calls=1, tool_calls=1))
runtime = Runtime(model, tools, budget=first)
result = runtime.run_session("计算", store=store, context=context)
# 只有可信入口决定继续后，才分配下一片段；累计账本不换。
second = ledger.start_segment(BudgetLimits(model_calls=1, tool_calls=0))
continued = Runtime(next_model, tools, budget=second)
```

显式budget是兼容选择：旧入口未传预算时保留原行为，不能因此声称全应用自动启用。可信入口必须为同一任务复用账本；SessionStore每次begin的新task_id与GoalProposal版本都不能未经设计当作累计任务ID。本步未绑定持久任务/会话归属，进程退出会丢内存账本；S19-b再处理身份、落盘和恢复，不伪造重启保证。

## 停止、恢复与错误边界

模型额度不足：在调用模型前停止，结果partial/budget_exhausted，trace的model及run为partial，model执行状态not_started；不把预算不足吞成model_call_failed。

工具批次中途不足：此前已完成结果保留；当前及后续请求各有一条ok=false/code=budget_exhausted/execution_state=not_started的配对消息。工具不启动、模型也不继续，所以会话历史仍可开启下一片段。若仅片段限额耗尽，recovery=new_segment_budget；若任务累计耗尽，recovery=review_task_budget，单建新片段不会解决，也不自动扩大总额。

预算检查只包住consume。已经启动的handler内部若抛BudgetExceeded或其他异常，仍按tool_execution_failed/unknown停止，不能假称not_started或自动重试。模型异常同样保留已扣派发额度，不根据是否看到答案退款。原权限门继续独立执行：预算充足的Plan写入仍waiting_user/plan_read_only。

此处验证Runtime不会自动重放已有工具结果，并不保证模型再次提出同一业务动作时exactly-once；幂等与未知执行结果恢复留S25。这里的partial也不是S20的完整语义检查点/暂停状态，未实现自动生成成果/缺口报告或自动授权续跑。

## 方案取舍

选择共享内存账本而非只扩client.max_requests：客户端可能更换，工具也不经过HTTP客户端，独立计数无法覆盖同一任务。选择调用前先扣而非结束后扣：远端失败/结果未知也有成本，结束后才扣容易越额；代价是本地准备失败也可能保守计入，不能把计数当精确费用。

选择一个共享锁保护各级计数，而非每级独立锁：代码更容易确认无并发超扣或交叉死锁；该锁只保护很短的计数操作，释放后才执行模型/handler，不把网络请求串行锁住。多进程/分布式锁和崩溃持久性不在此内存切片范围。

限额与快照复用已有Pydantic，未引入预算框架/SDK。旧wheel保留、正式库不改，回退无需DDL或数据清理；已有新模块格式不承诺旧wheel能理解。审查由主代理进行，没有独立子代理结论。
