## 任务推进流程

以下步骤用于内部判断，不要求向用户展示流程或逐项提问。先判断本轮最有帮助的一步，而不是一次覆盖全部步骤。

1. 理解用户想达成的结果
结合当前请求和已有上下文，判断用户的目标、当前进度及明确限制。
区分用户已经表达的事实和自己的推测，不把推测当成要求或授权。

2. 选择合适的下一步
- 请求明确、信息充分：直接回答，或在已有授权范围内推进。
- 符合上述澄清条件：简短承接目标，询问一个关键问题；最多附带一个紧密相关的问题。依赖该回答的部分等待用户答复，其他可独立完成且已获授权的部分继续推进。对仍待澄清的部分，不预设议题、行业或交付物，不提前展开通用清单、整套方案或额外提醒建议。用户明确要求先看通用清单时例外。
- 用户只是讨论或表达想法：帮助分析，不自动转成待办、提醒或执行任务。
- 发现与目标紧密相关的潜在困难：可以提出简短建议，让用户决定是否需要。
- 用户明确限定范围：尊重范围，不反复推荐额外帮助。

确认实际具备所需能力，以及当前操作是否得到应用授权。

4. 根据真实结果继续

不能因为工具被调用过，就认定操作成功；不能盲目重复可能产生副作用的操作。

对照用户目标和完成标准检查结果。

### 第2次响应原文

finish_reason：`stop`

你已经把复现条件固定到“空字符串 vs 正常字符串”，这很有用。下一步的重点是先拿到**具体异常**，暂时不必继续猜，再用输入变体判断失败发生在哪一层。

## 1. 先取异常的原始信息（优先级最高）

500 表示服务端抛出了未被捕获的异常，因此日志里应该有一条带堆栈的记录。请先找到它：

- 按请求时间和 traceId/requestId 找到那条 500 的**异常类名、message、堆栈最上层属于业务代码的帧**
- 同时保存：原始请求体、请求路径、环境（哪个版本、哪台机器）、发生时间

拿到堆栈最上层业务代码的那一行，基本就确定了问题。没有堆栈时，任何推断都只是猜测。

## 2. 分层二分步骤：判断失败发生在哪一层

按这个顺序做，每步只需一次对照实验：

| 实验 | 结果含义 |
|---|---|
| 绕过网关或前置中间件，直连服务端口发同样请求 | 仍然 500，说明问题在应用内；不再 500，说明问题在网关、WAF 或反序列化 |
| 单元测试中直接调用 handler，传入空字符串 | 能复现，说明问题在业务层；不能复现，问题在参数绑定或框架层 |
| 在 handler 入口打一行日志，记录收到的原始值 | 看到 `""` 说明传到了业务代码；看到 `null` 说明框架把空串转换成了 null；没打印说明更早就断掉 |
| 打印实际执行的 SQL 和参数（或看慢查询、数据库日志） | 如果原始值没错但 SQL 报错，说明问题在数据库层（例如空串被当作 NULL、非空约束、类型不匹配） |

## 3. 用输入变体缩小假设范围

保持其他字段不变，只替换当前字段，观察是否仍然 500：

- `null`、`""`、`" "`（单个空格）、超长串、正常串
- 换一个同样为空的**其他字段**：是所有空字段都 500，还是只有这个字段。
- 换一个**共用同一工具方法或同一个表的其他接口**：如果同样 500，说明是通用处理的问题；如果只有这个接口 500，说明是这个字段特有的逻辑。

这一步通常能把假设范围缩小到 3 到 4 条。典型对应关系如下：

- `null` 成功或异常，`""` 失败，`" "` 失败，常见于解析、格式化、`substring(0,1)`、`split` 取下标、数字或日期转换
- 只有 `""` 失败、`" "` 正常，常见于空值判空分支走了未处理路径，或数据库层把 `""` 当成 `NULL`
- 所有空字段都 500，常见于统一的绑定、序列化或响应组装层

每次实验都记录“假设、预期、实际”。如果实际结果和预期不符，就说明该假设被排除，这比反复分析代码更快。

## 4. 先确定接口约定，再修改

在修改之前需要判断：这个字段传空字符串**应该合法吗**？

- 不合法：应该返回 400 并给出明确错误，不能有 500，因为这是错误处理缺陷。
- 合法：业务逻辑里缺少空值分支，需要补上。

两种情况修的代码不同，先明确这一点再动手，避免出现“加了 `@NotBlank`，但实际空串本来就是合法输入”的改法反转。

## 5. 一个需要核对的点：偶发 500 可能不止一个原因
