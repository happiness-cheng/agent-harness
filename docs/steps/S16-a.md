## 为什么分开保存

| 概念 | 当前对象/字段 | 回答的问题 |
| --- | --- | --- |
| 工作模式 | WorkState.mode | 用户选择Plan还是Build？ |
| 目标提案 | GoalProposal/GoalSpec | 提议做什么、约束和完成标准是什么、允许哪些具体请求？ |
| 确认范围 | confirmed_goal_id | 用户确认的是当前哪个提案版本？ |
| 等待状态 | status/waiting_reason | 是否需要定向确认才能继续写操作？ |
| 单次运行状态 | 既有sessions.TaskState | 这次模型执行是否running/completed/failed等？ |

busy不是Build授权；一次模型运行结束也不代表用户已经确认目标。状态机不从历史文字中解析“同意”，不自动选择Build；可信入口显式调用select_mode或confirm，模型只可提出候选目标。接口不是登录系统，owner/session依旧由可信应用提供并通过SessionStore检查。

## 公共接口与状态转换

TaskController(sessions)关联既有可信会话，状态按session隔离，仅该控制器实例内共享。所有返回值深复制。

- snapshot(context)：读取当前WorkState；尚无目标时默认为Plan/ready，可直接查询，无须让普通聊天逐条确认。
- select_mode(context,"plan"或"build")：显式用户模式事件。Build没有已确认目标则waiting_user；切换模式不能抹掉既有越界等待。已有确认范围保持，不要求正常步骤反复确认。
- propose(context,GoalSpec)：重新校验目标，生成全新proposal_id、撤销旧确认并waiting_user。相同文本重新提案也有新版本，避免旧回复批准新提案。
- confirm(context,proposal_id)：只确认当前session的当前提案版本，进入ready；模式保持原值，Plan不会自动升级Build。重复定向确认当前版本可恢复原范围，但不扩大清单。
- authorize(context,ActionSpec)：只返回AuthorizationDecision，不运行handler、不发执行票据。todo.list在可信当前session可查询；写操作逐项检查模式、确认、等待和具体参数范围。

GoalSpec包含objective、constraints、completion_criteria和actions；目标/标准不能空白，完成标准至少一项。actions中的ActionSpec记录确定的todo操作及JSON参数；参数约定由真实入口规范化后传入，例如UUID转规范字符串、相对日期解析为绝对日期。文本用于解释用户意图，授权模块不声称理解或自动验证自然语言约束/完成标准。

| 当前情况/事件 | 实际结果 |
| --- | --- |
| 默认Plan请求todo.list | allowed，保持Plan |
| Plan请求任何写操作，即使范围已确认 | plan_read_only，保持Plan |
| 选择Build但无当前确认 | waiting_user；写入goal_unconfirmed |
| 提案后收到普通历史消息“同意” | 不改变确认状态 |
| 当前提案被定向确认 | ready；保持原Plan/Build模式 |
| Build/ready且具体请求匹配清单 | allowed，不要求每一步重新确认 |
| 操作、资源ID、参数字段或值越界 | scope_not_confirmed；保存waiting_user，不改已确认清单 |
| 已因越界等待，又请求原范围的写操作 | waiting_user；查询仍允许 |
| 提交新提案，再用旧proposal_id确认 | 拒绝；当前目标仍未确认 |
| 新提案获得匹配确认 | ready；在Build中允许其清单内请求 |

## 实际核心代码

写操作判定的前半部分，来自authorize：

```python
with self._lock:
    state = self._states.get(checked.session_id, WorkState())
    if state.mode == "plan":
        return AuthorizationDecision(allowed=False, code="plan_read_only")
    if state.confirmed_goal_id is None:
        return AuthorizationDecision(allowed=False, code="goal_unconfirmed")
    if state.status == "waiting_user":
        return AuthorizationDecision(allowed=False, code="waiting_user")
```

此前已检查context归属、重新校验ActionSpec，且仅无参数的todo.list走查询分支。写请求继续与提案清单比较；越界保存waiting_user及scope_not_confirmed原因，再返回拒绝，绝不把新请求自动加入允许清单。

confirm内的版本检查与发布：

```python
state = self._states.get(checked.session_id, WorkState())
if state.proposal is None or state.proposal.proposal_id != proposal_id:
    raise PermissionError("确认不属于当前目标版本")
candidate = WorkState(
    mode=state.mode, status="ready", proposal=state.proposal,
    confirmed_goal_id=proposal_id,
)
self._states[checked.session_id] = candidate
return candidate.model_copy(deep=True)
```

该代码在锁内执行；此前检查真实会话和UUID类型。mode=state.mode意味着确认本身不会把用户选的Plan升成Build。新提案使旧ID失效；跨session的确认也不能改变当前状态。

请求范围比较使用实际ActionSpec.signature：

```python
def signature(self) -> str:
    """保留JSON值类型，避免Python中True等于1造成范围误匹配。"""
    return json.dumps(
        self.model_dump(), sort_keys=True, ensure_ascii=False,
        allow_nan=False, separators=(",", ":"),
    )
```

这是用于相等比较的JSON文本，不是密码学签名、访问令牌或一次性凭证。字典键顺序不会改变匹配；True/1、1/1.0、None/字符串null不会混为一谈。ActionSpec重新校验并拒绝非有限数值、未知操作、顶层伪造mode/owner字段以及查询附带参数。

具体数据流：可信入口propose“修改该todo截止日为21日”及具体ID/参数 → 保存新提案、waiting_user → 用户定向confirm当前ID → 显式Build后请求同样参数，判定allowed → 若请求改为22日，拒绝并进入waiting_user → 新提案及新确认后可判定新日期允许。该过程没有实际更新todo；下一切片会把判定置于真实执行入口并处理提交边界。

## Python与C++类比

Pydantic严格模型可类比带验证的C++值对象，Literal约束模式/操作枚举，类型注解本身不负责运行时校验。入口将已有模型转回数据重新解析，能拒绝model_construct绕过校验的实例。GoalSpec默认元组表达不直接增删清单，但嵌套JSON字典仍可变；frozen=True也不等于深层不可变，因此propose切断输入别名，所有snapshot/返回值deep=True复制，避免外部拿到清单后偷偷修改权限。

RLock保护当前提案、确认及等待转换，可类比C++ recursive_mutex；先准备通过校验的新WorkState，再替换字典中的状态，避免无效输入半写。控制器锁和既有单次任务状态是不同职责，当前authorize只做判断，**并未把判断与后续业务执行合成原子操作**。

proposal_id可类比版本标记：只批准当前版本，不是看聊天里是否出现“同意”。它不替代身份认证，也不能靠知道一个UUID取得别人的权限。

## 方案取舍与限制

选结构化具体动作/参数清单，便于机械拒绝变更和编写可证伪测试。未选仅用自然语言目标或系统提示词授权：文字不能可靠地约束实际handler；也未新增通用权限表达式/状态机框架，避免在只有todo时增加概念。保守清单的代价是改变参数值要重新确认，不支持模糊范围、任意字段通配或自动推导未来资源权限。

GoalSpec文本与清单的一致性仍须可信入口展示并由用户确认；授权模块不会证明自然语言语义正确。清单内item_id匹配也不证明该todo属于当前session，真实TodoService必须继续验证资源归属和字段。查询允许仅覆盖当前本地todo.list，不向未来网络/隐私工具泛化“只读全放行”。

allowed只表示当前内存时点的判定；不能缓存后长期执行。S16-b需在执行边界重新检查，并明确并发模式变化/实际提交的顺序。这里不消费清单条目、不统计执行次数、不证明目标完成，也不承诺写操作恰好一次；重试和未知副作用恢复继续遵守后续步骤。

当前一个TaskController实例管理内存状态；另建实例或进程重启会回到默认Plan且无确认，不恢复旧权限。S15的业务持久化继续有效，但新目标/模式不会因此自动落盘。本步没有实际工具绑定、系统提示词加载、模型语义验证、waiting_user的Runtime结果接入、队列/取消或新数据库schema。
