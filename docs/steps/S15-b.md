## 实际核心代码与数据流

会话修改先构造独立候选快照；create/begin/append/finish最终都经过以下实际方法：

```python
def _commit_session(self, snapshot: SessionSnapshot) -> None:
    """调用方持有会话锁；提交成功后才发布候选状态。"""
    if self._storage is not None:
        self._storage.save(
            ExecutionContext(owner_id=snapshot.owner_id, session_id=snapshot.session_id),
            snapshot, list(self._todo_items.get(snapshot.session_id, {}).values()),
        )
    self._sessions[snapshot.session_id] = snapshot
```

例如begin用session.model_copy(deep=True)取得候选，再写入已校验的TaskState。save抛异常时，最后一行尚未执行，旧快照不会变；SQLite适配器自身会回滚事务。正常返回才表示本次修改已提交，而非仅改内存。

启动时storage.load_all()先验证全部记录，SessionStore再恢复消息、当前任务和完整待办，包括隐藏的逻辑删除项。即使还没构造TodoService，后续会话保存也不会遗漏待办。损坏库拒绝启动，不返回一个貌似全新的空会话库。

持久化模式的服务通过内部绑定共用集合和锁：

```python
def _bind_todos(self):
    """仅供TodoService内部绑定；持久化模式共用集合及同一把可重入锁。"""
    if self._storage is None:
        return {}, RLock()
    return self._todo_items, self._lock
```

同一SessionStore上两个持久化TodoService看到同一份当前事实；内存模式仍各有独立集合，原有生命周期测试保持通过。这是模块内部协作接口，不向模型或业务调用方返回可改的内部集合。

待办新增/修改/完成/删除先完整校验目标，再统一走：

```python
def _replace(self, context: ExecutionContext, item: TodoItem) -> None:
    """持有绑定锁，只发布已成功提交的候选集合；保留原有插入顺序。"""
    candidate = self._items.get(context.session_id, {}).copy()
    candidate[item.id] = item
    self._sessions._persist_todos(context, candidate)
    self._items[context.session_id] = candidate
```

_persist_todos在同一锁内重新检查会话归属，将当前会话快照与候选全部待办一起save。重复完成/删除提前返回changed=False，不产生SQL写入；新ID追加，旧ID的替换保留dict顺序，逻辑删除项仍保存在集合与数据库。

具体路径：todos.update(context,id,title="修改") → 检查owner/session及目标 → 校验新的TodoItem → 复制该会话的完整有序字典并替换该ID → SQLite同事务保存历史、任务及全部todo → COMMIT成功 → 替换内存字典 → 返回独立副本。中途触发SQLite错误时，内存字典仍为旧值，磁盘回滚；异常传给调用方。

并发会话历史和待办写入共用同一RLock，避免两者各拿旧快照覆盖对方。锁顺序为会话协调锁→SQLite适配器锁；存储内部只使用静态配对校验，不回调业务锁。构造TodoService绑定的是外层集合，后续替换会话内字典不会让另一个服务停留在旧字典上。

## Python机制与C++类比

- model_copy(deep=True)用于含可变消息的会话快照；候选里的TaskState和追加Message已先校验。TodoItem是冻结模型，替换记录而非就地改字段，候选dict浅复制即可；业务返回值仍是独立深副本。
- dict.copy()复制键值容器，给旧键赋新值保留位置，新键追加；身份不靠标题，两个同名项不会合并。
- RLock允许同一线程进入已有锁后再调用内部持锁方法；可类比C++ recursive_mutex，但不代表任意锁顺序都安全。这里明确共用协调锁，代价是同一个store的写入串行。
- 候选状态可类比C++“先准备临时值，成功后发布”。SQLite事务回滚负责磁盘，赋值顺序负责正常异常路径中的内存；二者不是同一个跨内存/磁盘事务。进程在COMMIT后被终止时，重启以已提交的磁盘事实恢复。
- TYPE_CHECKING中的SQLiteStorage/TodoItem导入只供类型工具，字符串注解避免运行时求值。实际运行依赖由storage参数传入，避免sessions→storage→todo→sessions循环导入；注解本身不做运行时校验，存储仍执行既有Pydantic校验。
- with SQLiteStorage.open(path)明确关闭连接，可类比RAII作用域；不能依靠Python垃圾回收时机保障落盘或关闭。

## 选择、未选方案与局限

采用既有SQLite适配器加一个SessionStore协调提交，减少新概念并复用此前验证。未选“先改内存、失败后再撤销”：撤销需要处理消息、任务、顺序和并发修改，容易遗漏；候选发布顺序更容易测试。未新增通用Repository/工作单元框架；当前只有两种业务事实，私有绑定接口足够，代价是两个业务模块有明确内部耦合。

每次完整快照复制、校验、序列化及同步提交，正确性路径清楚，但随着历史/待办增加会增加延迟和内存；同一store所有写入串行。当前恢复也一次加载全部记录，没有分页、按需加载或多实例冲突检测。**同一数据库由一个活动SessionStore协调**；多个store/进程独立缓存时不承诺合并，即使SQLite自身事务仍有效。

默认内存模式便于既有测试与显式选择；启用持久化必须传storage，正式库不会仅因存在就自动成为默认数据源。本步不新增Web启动入口、UI、模型工具授权、加密、清理、云同步、trace持久化或提醒。

Runtime未改代码，现有begin/append/finish调用自动经过持久化。它们是三次独立业务提交，并非整次模型运行的单一事务：begin失败时不调用模型；append失败保留running与旧历史；finish失败时历史可能已提交而任务仍running。异常向调用方传播，不返回completed；trace中的模型/run阶段结果不能冒充数据库最终提交状态。

running、failed和未配对工具请求按原事实恢复；不自动解除busy、重放模型或重试工具。进程中断、模型已回答但保存失败、外部副作用结果未知的续跑策略留S25，不以本步数据库回滚承诺外部操作也能撤销。

due_date保存绝对日期；恢复后overdue用新注入时钟重算，不把“今天”重新解释一次，也不存派生逾期标记。
