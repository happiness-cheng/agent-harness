## 三个公共对象

| 对象 | 必填字段 | 可选字段及默认值 | 本步规则 |
| --- | --- | --- | --- |
| Message | role、content | tool_call_id=None | 四种内部角色 system/user/assistant/tool；只有 tool 必须且可以携带调用 ID |
| ToolCall | id、name、arguments | 无 | ID/名称非空白；arguments 为 JSON 值类型的字典；拒绝非有限浮点 |
| ModelResponse | finish_reason | content=None、tool_calls=独立空列表、reasoning_summary=None | 正文可与工具请求并存；检查结束原因与数据是否一致，调用 ID 不重复 |

## 核心代码与 Python 机制

Message：

```python
class Message(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")

    role: Literal["system", "user", "assistant", "tool"]
    content: str
    tool_call_id: str | None = Field(default=None, min_length=1, pattern=r"\S")

    @model_validator(mode="after")
    def validate_tool_reference(self) -> Self:
        if self.role == "tool" and self.tool_call_id is None:
            raise ValueError("工具消息必须提供 tool_call_id")
        if self.role != "tool" and self.tool_call_id is not None:
            raise ValueError("只有工具消息可以提供 tool_call_id")
        return self
```

`Literal` 限定允许值；`str | None` 表示字符串或 None；没有默认值的字段为必填。普通 Python 类型注解本身不会进行运行时检查，这里由 BaseModel 在构造/解析时执行。

strict=True 避免未经明确允许的类型转换，extra=forbid 拒绝拼错或夹带的字段。`\S` 检查至少含一个非空白字符，不裁剪 ID；正文也原样保留。after 校验器在各字段通过类型校验后检查跨字段关系，成功返回当前对象，失败抛 ValueError，由 Pydantic 汇总为 ValidationError。

ToolCall：

```python
class ToolCall(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid", allow_inf_nan=False)

    id: str = Field(min_length=1, pattern=r"\S")
    name: str = Field(min_length=1, pattern=r"\S")
    arguments: dict[str, JsonValue]
```

JsonValue 是 Pydantic 提供的递归 JSON 值类型，可含列表、字典、数字、字符串、布尔值和 null。arguments 必须先是对象，不能直接接收 JSON 编码后的字符串；S17 解析 provider 的参数字符串后再构造此对象。数据通过校验不代表工具存在或获准执行，具体 Schema、权限和预算属于后续步骤。

自审实测发现默认配置把 NaN 序列化为 null，改变参数含义。因此先增加 NaN 和嵌套无穷大的失败测试，再用 allow_inf_nan=False 拒绝这些输入。没有改写数值来掩盖错误。

ModelResponse 的字段及关键校验：

```python
class ModelResponse(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")

    finish_reason: Literal["stop", "tool_calls", "length", "refusal", "error"]
    content: str | None = None
    tool_calls: list[ToolCall] = Field(default_factory=list)
    reasoning_summary: str | None = None

    @model_validator(mode="after")
    def validate_response_shape(self) -> Self:
        if self.finish_reason == "stop":
            if self.content is None or not self.content.strip():
                raise ValueError("stop 响应必须包含非空白正文")
            if self.tool_calls:
                raise ValueError("包含工具请求的响应不能标为 stop")
        if self.finish_reason == "tool_calls" and not self.tool_calls:
            raise ValueError("tool_calls 响应必须包含工具请求")

        call_ids = [call.id for call in self.tool_calls]
        if len(call_ids) != len(set(call_ids)):
            raise ValueError("同一次响应的工具调用 ID 不能重复")
        return self
```

`default_factory=list` 为每个响应产生独立列表。列表推导提取 ID，set 去重后比较长度，拒绝调用/结果配对的歧义。没有增加另一份 is_success 状态，避免它和结束原因矛盾。

length/refusal/error 可以保留部分正文和已解析的调用，便于追踪真实返回。后续 Runtime 必须先检查结束原因，不能看到 tool_calls 非空就启动工具，也不能把部分输出当成任务完成。reasoning_summary 只承载 provider 实际公开提供的摘要，不请求或伪造隐藏思维链。

## 一次具体的数据流

```python
call = ToolCall(id="demo-1", name="calculator", arguments={"expression": "1+2"})
response = ModelResponse(
    finish_reason="tool_calls", content="先计算。", tool_calls=[call]
)
result_message = Message(role="tool", content="3", tool_call_id=call.id)
```

构造调用 → 校验 ID、名称和参数类型 → 将调用放入模型响应 → 检查结束原因和 ID 唯一性 → 用相同调用 ID 构造工具结果消息。此例已在真实 Python 进程中运行；“3”是手工提供的示例内容，没有执行 calculator。工具执行与跨消息配对将在 S06 完成。

错误路径示例：Message(role="tool", content="3") 缺少调用 ID，实际抛出 ValidationError，其错误说明为“工具消息必须提供 tool_call_id”。本步不把校验失败转换成成功响应，也不自动修补不明确的 ID。

## 选用方案、未选方案与取舍

选 Pydantic 而不是普通 dict：可以把错误集中在数据入口，避免后续到处检查键名和类型。选择 dataclass 也可更轻量，但还要另写嵌套 JSON、错误定位和序列化校验。代价是新增 Pydantic 及其原生扩展依赖，当前原生 Windows wheel 已实际安装并运行。

选择三个直接的 BaseModel 子类，没有引入通用基类；配置重复很少，便于逐个阅读。若后续出现大量共同规则再考虑抽取。

正文、工具请求、结束原因分别保存，允许正常的混合输出。另一种方案是用一个 text/tool 标签强迫二选一，会丢掉模型在工具调用前提供的说明。代价是需要明确跨字段规则，当前校验器承担这一职责。

C++ 类比：这三个对象接近 struct，Literal 接近受限枚举，JsonValue 接近递归的 variant。差异在于 Python 注解不提供 C++ 式编译期保证，Pydantic 在运行时校验；对象和其列表/字典仍可变，不能类比成 const 值对象。

已知局限：仅在构造/解析边界校验，没有开启赋值检查或深层不可变；就地修改后不能假定约束仍成立。Message 尚不包含完整 assistant 工具调用历史；跨消息 ID 是否实际存在、会话归属、工具权限、大小/深度预算、真实 provider 映射均未实现。不将拒绝额外 session_id 字段误称为已经实现会话授权。

官方依据：[Pydantic Models §Basic model usage / Extra data / Validating data](https://docs.pydantic.dev/latest/concepts/models/)、[Validators §Model validators](https://docs.pydantic.dev/latest/concepts/validators/#model-validators)、[Types §JsonValue](https://docs.pydantic.dev/latest/api/types/#pydantic.types.JsonValue)。
