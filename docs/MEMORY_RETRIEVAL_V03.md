## P1：可解释排序

新模块 `src/min_agent/long_memory/retrieval_quality.py`，公共离线入口 `experiment_search`。默认生产模块不导入它。

原排序器只依赖原词项重叠与 BM25，常把包含大量“我要、帮我、什么号码”的问句排在携带答案的短原句前。实验排序尝试以下信号：

| 信号 | 设计理由 | 本轮局限 |
|---|---|---|
| 去通用词的查询 IDF 覆盖 | 降低礼貌语/通用动词的干扰 | 简单词形处理与缩写切分仍有噪声，非完整语言理解 |
| 同源会话相邻原句覆盖 | 给纯数值回答提供局部问题线索 | 邻接不等于正确语义关联，可能把别的属性传过来 |
| 属性词族匹配 | 区分编号、时间、费用、保障、权益等需求 | “编号”过宽，会员号与预订号仍混淆 |
| 相关的数值/否定/约束 | 倾向携带具体取值的片段 | 地址、历史状态也可能被误提权；数值不等于正确事实 |
| 实体或显式别名匹配 | 优先处理同一实体的候选 | 邻居的实体可能误影响当前片段 |
| 原排序小权重 | 保留已有信号，方便解释差异 | 权重未经过泛化验证 |
| 整段问句惩罚 | 避免反复召回提问本身 | 错伤前半句已陈述事实、末尾另有问句的消息 |

冻结分数如下；不是 Goal-Value 的重要性权重：

```python
WEIGHTS = {
    'query_overlap': 2.0, 'neighbor_overlap': 1.0,
    'attribute_match': 1.0, 'specific_value': 0.75,
    'entity_match': 2.0, 'old_score': 0.2, 'is_question': -0.6,
}
total = sum(WEIGHTS[key] * feature[key] for key in WEIGHTS)
```

B 只改变 cap 后原候选内部的顺序，不增加候选、不改原文。所有特征和邻居 ID 随结果保存；它们仅作排序线索，不写入事实数据库、不授予权限。新 `total` 与旧 `score` 分开记录。

## P2：候选召回与融合

1. 原路径保留；第二路按通用属性词族扩展查询，不含案例 ID、具体品牌、人名或答案数值。
2. 仅从截至查询时点的授权原文识别显式 `Name (ALIAS)`，避免世界知识猜测别名。
3. 取原路径与扩展路径各至多12个有关键词支持的锚点，沿同一源历史会话的消息索引 ±1 加候选；保留原始 Episode，不复制邻居正文进模型。
4. 三路各自按 memory_id 去重，以 `RRF(k=60)` 在同一 cap=100 内决定成员。路径不要求严格超集，旧重要证据也可能被竞争掉，报告保留这类失败。

C 的排序仍用旧分数：原完整融合池存在该 ID 就保留原分数；新词项候选用同一 `_lookup` 在原查询下的分数；纯邻接而无原词命中者为0。RRF 只控制成员，不偷偷作为 C 的最终排序分数。D 对与 C 完全相同的候选再使用新排序。

实现未扩大 Top-K 或最终 cap。候选扩展的额外扫描、FTS、邻接及融合成本都包含在延迟记录中。底层内存 FTS 按调用重建，当前延迟不是缓存优化后的生产指标。

## P3：原子卡片独立探索

`atomic_cards.py` 提供 `subject / attribute / value`，场景、有效时间、原文字符引用、源版本 hash、evidence_type、claim_kind 和 confirmation_status。

每个字段都必须逐字对上合法来源。不同源会话拒绝关联；跨句或 assistant 来源不能直接标为明确用户事实；输出始终 `pending`。后续读取通过 validate_atomic_card 重新校验，撤回/过期/来源变化后失效。构建过程不写生产 Memory。

实际构建了受控 Orchid Travel / tier / Bronze，以及原 Amex 对话的 `American Express / card / Gold Card`。后者分别引用消息1、0、16，保留 `inferred + pending`；没有把 Gold 答案“Amex Gold”复制成新确定事实。另测跨事件、伪造字段、推断升级、未批准等拒绝路径，结果6/6受控检查通过。

**这验证的是引用和构建约束，不是自动抽取能力。** 字段位置由受控 recipe 指定；同一源会话也不必然等于同一业务事件，任意跨句语义正确性还需要进一步审核。卡片不进入四组检索，公开实验日志也不属于生产删除链路；生产删除机制与边界本轮不变。
