# 架构设计题：我的方案与推敲

五个模块各选一道题，沿用初稿“核心问题→设计方案→原理→取舍→工程边界”的完整论证。每题补充我在讨论中的追问和选择，让方案背后的判断也能被看到。第五题先修正比较对象、直接回答协议差异，再保留Adapter的延伸思考。

文中的“我”指项目作者。两份可见聊天包含本人的表达、AI的追问和归纳，来源分开标注；讨论中的初始判断和后续纠正保留在原聊天。整体四层思路见 [我想构建什么样的Agent](AGENT_VISION.md)，当前代码和未实现项见 [提交说明](SUBMISSION.md)。以下方案描述目标架构，不意味着最小版本已实现全部能力。

## 模块一 · 第2题：200轮对话，Context即将耗尽，如何压缩？

### 1. 核心问题

LLM 的 Context Window 有上限，但 Agent 可能持续执行很长时间。

我们真正要解决的不是简单删减 Token，而是：

在有限 Context 中，保留完成当前任务所必需的信息，同时保证历史状态与决策连续性。

### 2. 设计方案：分层压缩

~~~text
原始对话 + 工具结果

第一级：确定性压缩

移除冗余日志、裁剪超长工具输出、保留原始引用

第二级：结构化事件摘要

保留重要决策、状态变化、证据及事件关系

第三级：LLM 全量压缩

作为最后手段，重建任务相关的紧凑上下文

~~~

关键是把以下三类数据分开管理：

- Event Log：记录发生过什么，尽量保留完整历史。
- Task State：记录当前目标、进度、约束、待办和已验证结果。
- Context：从前两者选择并构造给模型看的有限工作视图。

### 3. 底层原理

这与数据库的事实数据和物化视图有相似之处：

Event Log 是可追溯的历史记录，Context 是面向当前推理任务生成的视图。

压缩改变的是模型看到的视图，不应该直接篡改权威任务状态。

### 4. Trade-off

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 删除冗余内容 | 快、成本低 | 信息压缩能力有限 |
| 结构化摘要 | 可追溯，较易恢复决策链 | 摘要维护更复杂 |
| LLM 全量压缩 | 压缩率较高，能够语义概括 | 可能遗漏、歪曲事实，增加 Token 成本 |

### 5. 工程边界

建议在 Context 使用率达到一定阈值时触发预警，例如 80%，但实际阈值需要考虑工具 Schema、预留输出空间和模型差异。

压缩应在安全执行边界上进行，并使用版本校验，避免把压缩期间的新消息遗漏掉。

如果压缩失败，保留原始记录，允许回退或安全暂停，不应直接覆盖原数据。

Context 是可重建的工作视图，不是唯一事实来源。

### 我的推敲与取舍

> 摘要不是简单的总结概括内容，而是结合任务目标，用户要求做上下文感知压缩

我在讨论中没有给所有任务选同一种压缩方案。全量阅读可能更不容易漏关键风险，但成本、延迟和模型窗口都有限；先分块提取更便宜，却必须验证提取阶段是否遗漏，因为模型无法从未收到的信息中恢复事实。面对冲突，我选择保留并查明原因，而不是让摘要自行消解。

触发时机也要看当前任务还需多少工作：接近阈值先做轻量处理，仍不足再升级；80%是讨论用的预警值，不是可以预测所有任务的保证。保留原文、当前状态及压缩失败熔断，使压缩成为可核对的过程。

来源：[架构推演 · 用户014、018、020、022、024、045](ai-conversations/02-architecture.md)。

**项目实践边界：**冻结工具预览、逐轮归档、分层压缩及失败熔断已有实现；当前使用字节估算，没有200轮真实模型或缓存命中实测。动态早期状态仍影响缓存前缀，相关后续设计不能计为已完成。

## 模块二 · 第1题：用户半个月后重新提问，如何利用Memory恢复上下文？

### 1. 核心问题

用户的新问题可能依赖很久以前的对话，但不能每次都把完整历史塞给 LLM。

核心是：

从大量历史中找出与当前任务相关、可信、仍然有效的记忆。

### 2. 设计方案：分层 Memory + 按需检索

区分三类记忆：

| Memory 类型 | 保存内容 | 例子 |
| --- | --- | --- |
| Global Memory | 长期偏好、稳定约束 | 用户偏好通过实际工程理解技术 |
| Project Memory | 特定项目的架构和决策 | Agent Harness 采用独立 Model Adapter |
| Session Memory | 本次任务的近期信息 | 当前正在调试 Calculator |

执行流程：

~~~text
用户新问题
   ↓
识别用户意图、项目和所需历史
   ↓
选择检索范围
   ↓
关键词 / 语义 / 结构化检索
   ↓
相关性、时间、来源、权限检查
   ↓
选择性注入 Context
   ↓
生成回答或执行下一步

~~~

### 3. 底层原理

Memory 可以看作一个持续更新的信息检索系统。

关键不只是存储，而是四件事：

- 写入：哪些事实值得长期保存？
- 检索：哪些记忆与当前问题有关？
- 更新：新旧事实发生冲突怎么办？
- 使用：哪些记忆应该影响本次决策？

例如：

~~~text
V10：用户偏好 C++
V11：用户偏好 Python

~~~

Memory 更新不意味着所有运行中的任务都必须重新规划。

如果当前任务明确要求使用 C++，长期偏好变化不应覆盖当前硬约束。

### 4. Trade-off

主动保存大量记忆能提高召回可能性，但会产生噪声、过期信息和隐私成本。

严格筛选记忆有利于准确性，但也可能漏掉未来重要的信息。

因此需要结合来源、作用范围、置信度、更新时间以及任务相关性进行判断。

### 5. 工程边界

- 不把模型推断出的偏好直接当成用户确认的事实。
- 遇到冲突时保留来源和版本，必要时标记 DISPUTED。
- 对重要事实支持重新验证，而不是简单相信最新一条。
- 通过 Recall@k、MRR、过期记忆误用率和最终任务成功率评估效果。

Memory 的价值不在于记住所有历史，而在于在正确的时候提供正确的信息。

### 我的推敲与取舍

> Memory的核心是为了更好的服务当前的任务

我不只关心选哪种检索算法，还追问“模型怎么知道存在可用记忆”和“哪些内容应该提前保存”。我的写入标准包括当前价值、长期价值、复用可能与时效性。用户明确限定的项目语言，优先于长期偏好；用户也应能决定哪些内容可以记住、哪些不得保存。

评价应包括该召回的是否召回、是否混入无关内容、回答质量及用户体验。如果表现不好，先区分是检索、上下文组装还是模型使用出错，再控制变量逐项修复。不能只因为增加记忆后回答变长，就认为记忆有效。

来源：[架构推演 · 用户049、051、054、060、062、064、066](ai-conversations/02-architecture.md)。

**项目实践边界：**当前仅有Session内归档与按需回查。用户级、项目级长期记忆是目标设计；稳定旧答案可复用，时效事实需要重新核实。“最熟悉C++”与“本项目采用Python”是不同作用域的事实，不必判为冲突。

## 模块三 · 第1题：长程任务执行中，Agent忘记最初目标，怎么办？

### 1. 核心问题

Agent 可能执行了大量工具、经历多轮压缩和重新规划，却逐渐偏离用户真正想完成的事情。

尤其不能把模型声称的“任务完成”当作真实成功。

### 2. 设计方案：Goal、Plan、State 分离

这是这一题最核心的架构设计。

| 对象 | 职责 | 能否修改 |
| --- | --- | --- |
| Goal | 用户最终想达到什么结果 | 通常只有用户授权才能修改 |
| Plan | 通过哪些步骤实现 Goal | 可以随着执行结果动态调整 |
| State | 当前真实执行进度 | 根据事件、证据和验证结果更新 |

例如用户要求：
实现一个可运行的 Agent Harness，包含工具调用、Session 和测试。

~~~yaml
goal:
  deliverable: 可运行的 Agent Harness

plan:
  - 实现 Agent Loop
  - 实现 Tool Registry
  - 添加 Calculator / Search / Todo
  - 接入真实 LLM
  - 编写测试

state:
  loop: VERIFIED
  tool_registry: VERIFIED
  calculator: VERIFIED
  llm_api: NOT_STARTED
  tests: PARTIAL

~~~

即使模型在中途压缩 Context，Runtime 也能根据持久化状态恢复目标和进度。

### 3. 底层原理：闭环控制

Agent 不应该只是：
计划 → 执行 → 声称成功

而应该是：

~~~text
Goal
 ↓
Plan
 ↓
Execute
 ↓
Verify
 ↓
Update State
 ↓
继续 / 重规划 / 结束

~~~

Verify 是关键。

例如测试通过，只能证明相关测试通过，不能直接证明整个项目满足所有需求。

### 4. Trade-off

过于严格的验证会增加工具调用和延迟。

过于宽松又容易产生虚假的完成状态。

因此应当根据操作风险和验收要求选择不同强度的验证。

### 5. 工程边界

- 每项任务设置明确验收条件。
- COMPLETED 与 VERIFIED 区分。
- 保存工具执行证据及其对应版本。
- 设置最大循环次数、Token 和时间预算。
- 多轮无有效进展时触发重规划。
- 无法验证的任务标记为未确认，不伪装成功。

**面试核心表达：**Goal 保证方向，Plan 负责策略，State 和 Verifier 保证执行结果可信。

### 我的推敲与取舍

> 核验测试内容以及测试版本以及用户真实目标需求

这是我对“测试通过就能算完成吗”的进一步判断。我接受有利于目标的计划调整，但不能接受目标被悄悄改变，还要考虑时间和资源。验收证据既要正确，也要与本次版本、测试范围和用户需求对应。

我在讨论中也明确承认，如何把模糊需求变成可执行验收规则，需要继续学习。当前的设计先把目标和完成条件写清楚，能用代码或明确规则检查的先检查；无法核实的部分留下不确定状态，不让模型凭一句自评结束。

来源：[架构推演 · 用户026、035、070、074、076](ai-conversations/02-architecture.md)。

**项目实践边界：**目标确认、授权动作、检查点、调用预算及无进展检测已有实现；completed仍只表示模型正常结束。通用独立Verifier和累计Token／费用／任务时间硬门尚未实现。

## 模块四 · 第2题：Session正在busy，新的用户消息或异步工具结果到达，如何处理？

### 1. 核心问题

Agent 正在执行一个耗时任务时，可能同时出现：

- 用户修改要求。
- 旧工具尚未执行完。
- 另一个工具返回结果。
- 新任务需要立即开始。
- 用户要求取消原任务。
如果多个执行流程直接修改同一份 Session 状态，就可能出现竞态条件、消息串扰和重复工具执行。

### 2. 设计方案：事件队列 + Run 隔离 + 异步工具

我会采用以下架构：

~~~text
用户新消息 / 工具完成事件 / 取消 / 超时
                    ↓
Session Event Queue（持久化事件，保证归属与顺序）
                    ↓
Session Actor / State Reducer（串行处理该 Session 的共享状态变化）
          ├─ Run 001：ReadDocs 异步执行
          └─ Run 002：Calculator 独立执行

~~~

这里的设计是：

同一 Session 的共享状态修改串行化，但不同 Run 的独立计算与工具执行可以并发。

工具执行结果不能随意追加到全局消息列表，而要通过 run_id、tool_call_id 回到正确的执行上下文。

### 3. 新消息的处理策略

生产上可以根据任务关系选择不同策略：

| 策略 | 适用场景 | 代价 |
| --- | --- | --- |
| Queue 排队 | 新请求依赖旧任务结果 | 用户需要等待 |
| Cancel 取消 | 用户明确要求停止或修改旧任务 | 需要处理迟到结果和外部副作用 |
| Parallel 并行 | 新旧任务彼此独立 | 需要隔离状态并处理资源竞争 |

例如用户原先要求写 1000 字报告，后来改成 500 字。

Runtime 不应该盲目执行两份报告，而应该把新指令合并进当前目标状态，在安全点重新规划。

### 4. 底层原理

这与并发编程的 Actor Model、事件驱动架构有相似之处：

- Event Queue 接收外部事件。
- Session Actor 负责共享状态的串行更新。
- 异步工具负责耗时的外部操作。
- Event Log 记录已发生的状态转换。
- Version / CAS 防止过期操作覆盖新状态。
Actor 串行处理可以减少共享状态竞态，但不能自动保证外部工具的幂等性，也不能解决所有分布式一致性问题。

### 5. 工程边界：取消不等于撤销

假设 Agent 调用支付工具，用户随后要求取消。

即使 Runtime 取消了本地等待，也不代表支付平台没有完成扣款。

正确做法是：

1. 记录该工具请求的幂等键。
2. 将结果不确定的操作标记为 UNKNOWN。
3. 查询外部真实执行状态。
4. 依据结果决定确认、补偿或重试。
5. 不允许旧 Run 的迟到结果污染新 Run。

**面试核心表达：**Session 共享状态串行化，Run 执行上下文隔离，工具可以异步并行，但结果必须有归属，副作用必须可追踪。

### 我的推敲与取舍

> 同一操作使用同一key，即使超时重试也不切换别的key

我在讨论中关心的不只是串行还是并行，还包括：怎么知道另一个Run读到了旧版本？状态或Memory变化是否真的影响当前任务？用户偏好改变，不能自行改变一个已明确要求C++的任务。

对于明显替代旧要求的控制指令，没有必要把所有已经失效的任务都交给模型继续执行；但控制事件和普通排队消息需要区分。最终本项目采用我在需求阶段提出的默认策略：让当前整项任务完成，除非用户主动停止或引导。

来源：[需求共创 · 用户053](ai-conversations/01-design.md)；[架构推演 · 用户080、084、088、094、096](ai-conversations/02-architecture.md)。

**项目实践边界：**上文“改成500字”的例子描述支持任务修改事件的目标设计。当前版本普通消息仍排队，只有显式Steer／Stop改变当前执行；没有自动意图合并、同Session并行主任务或通用异步工具事件总线。

## 模块五 · 第1题：Claude Code与GLM／豆包的工具输出方式有什么不同，各有什么优缺点？

先分清产品界面、模型API和Runtime。Claude Code是应用，OpenAI-compatible function calling是接口约定；不能把可见界面等同产品全部内部实现。以下比较公开的Anthropic Messages客户端工具协议与GLM／豆包Chat Completions接口，不推断Claude Code未公开的内部细节。

| 对比点 | Anthropic Messages | GLM／豆包Chat Completions |
| --- | --- | --- |
| 模型请求工具 | assistant content内的tool_use块，input为对象 | assistant.tool_calls，function.arguments为JSON字符串 |
| 回传工具结果 | user消息内的tool_result，通过tool_use_id配对 | role=tool消息，通过tool_call_id配对 |
| 内容组织 | 消息按类型化内容块组合 | 文本与调用字段分别表示，其他类型依具体接口核对 |
| 执行错误 | tool_result支持is_error | 应用可在工具结果内容中约定结构化错误，依供应商扩展核对 |

两者均由模型提出调用请求，由客户端Runtime校验参数、检查权限、执行工具并回传结果。Anthropic的user角色在这里承载工具结果，不代表用户又发送了一条自然语言指令。两边都要维护调用与结果的配对，不能跳过失败的工具而留下不完整历史。

我的工程判断：内容块更适合表达类型与顺序，但解析、流式处理、归档和多模态适配更复杂；常见兼容接口便于复用SDK和服务生态，但JSON字符串仍需安全解析和Schema校验，“兼容”也不保证结束原因、推理字段和并行工具行为一致。不能据协议形式断言某家更快、更可靠。

项目选择轻量内部消息加双向Model Adapter，同时处理“厂商响应→内部对象”和“历史及工具结果→下次厂商请求”。保留必要原生字段，无法安全转换则拒绝；模型call ID负责协议配对，确认动作实例负责授权次数。切换模型只迁移可解释的历史、任务状态和证据，不直接转发另一家专用状态或盲重试未知写入。

MCP属于工具发现和调用层，不能替代模型消息Adapter。当前项目实际接入DeepSeek／OpenAI Responses；本题的Chat Completions比较不能直接套用到Responses，也不代表已实现Anthropic、GLM或豆包适配。

依据（核对于2026-10-21）：[Anthropic §Handling results from client tools／Handling errors with is_error](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)、[GLM §响应参数说明／代码示例](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)、[豆包Chat API §messages.tool_calls／messages.tool_call_id／choices.message.tool_calls](https://docs.volcengine.com/docs/ark/chat-api?lang=zh)。以上优缺点为工程评价，没有虚构性能对比。

### 我的选择与后续推演

> 我觉得function calling的本质是函数调用，是Runtime 根据模型生成的结构化请求执行了工具；我觉得设计一层独立的 Model Adapter 统一转换

这是我在讨论中提出的分工。随后我先选择简单的content + tool_calls，理由是当前需求够用，代价是未来扩展性较差；再继续讨论如何保留必要原生状态、怎样迁移到另一种模型，避免为了统一而丢失协议要求。

| 抽象方案 | 优点 | 代价 |
| --- | --- | --- |
| A：content + tool_calls | 简单，适合最小Agent | 对复杂内容和多模态表达有限 |
| B：统一语义 + 必要原生状态 | 保持主循环简单，兼顾协议往返 | 必须管理供应商状态与迁移边界 |
| C：统一Content Block模型 | 表达能力强 | 实现、测试与维护更复杂 |

当前实现保留简单语义对象及经过校验的提供商状态，没有扩展成通用Content Block系统。换模型的恢复还需要对照Event Log与实际数据库状态，再检查幂等性；不能只换一个API地址就假设可以继续。

来源：[架构推演 · 用户098、102、109、111、115](ai-conversations/02-architecture.md)。MCP与模型协议适配的关系可以继续研究，但不能取代本题要求的工具输出差异与优缺点比较。

## 五题怎样串成一个Agent

第一题把Context当作可重建的工作视图；第二题决定哪些历史知识值得召回；第三题保存当前目标、计划、真实进展与验收；第四题约束事件怎样改变状态；第五题把模型协议与核心循环隔开。

它们共同支撑我最初提出的“决策与上下文、知识与能力、执行与运行时”，再把可追查的证据交给“评估与进化”。这也是我希望项目在笔试结束后继续发展的方向。
