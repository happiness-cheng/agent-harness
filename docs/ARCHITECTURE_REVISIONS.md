# 架构设计题

每个模块选择一道题。以下区分目标设计和项目实际实现；原始推演保留在 [AI 对话](ai-conversations/README.md)，实现范围见 [提交说明](SUBMISSION.md)。

## 模块一 · 第2题：200轮对话，Context即将耗尽，如何压缩？

核心不是尽量删Token，而是保住当前任务的约束、状态与证据。我把原始事件、权威任务状态、模型可见Context分开：压缩修改工作视图，不修改授权和真实业务结果。

请求前计算完整输入，包括工具Schema、计划注入的记忆，并预留输出和安全余量。处理顺序是：

1. 大工具结果落盘，首次生成有引用的冻结预览；后续补读追加消息。导航栏、重复日志等噪声在进入冻结视图前过滤，避免逐轮改写旧前缀。
2. 每个完整交互独立归档用户决策、约束、状态变化和证据位置，保留最近交互，相关历史按需回查。摘要不是独立验证后的事实。
3. 仍超窗时先整理会话记忆，再由LLM压缩旧的完整交互。保留日期、实体、否定、纠正、未完成事项及出处；不能拆散工具调用与结果。

压缩以源范围、哈希和版本校验，验证通过才切换投影；失败保留原版，同一输入连续失败则熔断暂停。压缩也消耗预算，不允许无限重试。如果采用服务端上下文编辑，需适配具体API，不能假设删除旧结果后仍保留其后缓存。

流畅性要用追问验证：压缩前后对相同日期、人物、否定和纠正应保持一致；既能直接回答历史问题，也能依据原约束继续调用工具，缺证据时能回查而非猜测。检索任务保广度，分析任务保论证与反例，不能用同一摘要模板裁剪所有任务。

取舍：确定性处理便宜但压缩率有限；LLM语义压缩更强，但有调用成本和语义失真。当前项目采用保守字节估算、冻结工具预览、逐轮归档及分层压缩；尚无200轮真实模型实测。早期动态application_state仍会影响其后缓存，不能声称整个请求前缀已稳定。

## 模块二 · 第1题：半个月后用户问过同一问题，Memory如何召回？

先判断用户需要复用历史答案，还是重新获取当前事实。重复措辞不等于同一意图：过去问天气与今天问天气，历史可以帮助确定城市，却不能代替今天的天气。

目标设计将记忆按用户、项目和会话限定作用域。收到新问题后，先用近期上下文和项目标识缩小范围，再检索旧问题、答案、证据及后续纠正。关键词适合专有名词，语义检索补充改写，结构化条件处理日期和任务ID。按相关性、出处、有效期和置信度排序，并在读取时检查权限。

稳定结论可以复用；价格、岗位、政策等时效事实需要刷新来源。用户当前明确要求优先；“最熟悉C++”和“这个项目选择Python”是不同作用域的事实，不应互相覆盖。冲突记忆保留版本、来源和争议状态；模型推断的偏好不能自动升为用户确认。

召回结果以有来源和时间的参考块放入本次工作上下文，不冒充系统指令，也不因每次检索而改写稳定系统前缀。无匹配时不塞无关记录；高影响冲突才向用户澄清。评估除Recall@k、MRR，还要看过期记忆误用率、冲突处理和最终任务成功率。

取舍：多存有利于召回，但增加噪声、权限和过期处理成本；严格筛选可能漏掉后续需要的信息。当前项目仅实现会话内归档、相关回查及原文引用，尚未实现跨会话长期画像或向量检索。

## 模块三 · 第1题：长程任务中模型忘记目标，如何解决？

我会组合使用持久任务状态、目标重申、检查点和验证闭环。单靠反复提示目标，无法阻止模型错误更新状态；单靠计划，也可能认真完成错误的方向。

| 对象 | 保存什么 | 更新边界 |
| --- | --- | --- |
| Goal | 用户目标、约束、完成标准和确认版本 | 改变目标或扩大动作范围需要用户授权 |
| Plan | 下一步及依赖关系 | 可根据证据重规划 |
| State | 已执行动作、实际结果、未知状态和阻塞 | 依据业务状态和工具证据更新 |
| Verify | 验收条件及对应证据 | 模型声称完成不等于独立验证 |

每次运行恢复、压缩后、重规划前，以及即将执行重要动作时，重新构造当前目标与进展。模型生成计划，Runtime限制授权范围、次数和预算；关键动作后记录实际结果。检查点保存目标版本、证据引用及原预算，恢复前先核对未知副作用，不重新执行已成功动作。

发现连续相同调用且无状态变化时，给一次纠错机会，再无进展则暂停。接近预算先预留一次无工具整理，报告成果、缺口和下一步；硬门不可由模型取消。复杂任务通过用户允许的后续片段继续，而不是把恢复变成无限重置累计额度。

取舍：频繁注入目标占用窗口，验证增加延迟；低风险步骤可批量验证，重要写入需更强证据。检查点提高可恢复性，但不能保证所有外部副作用可回滚。当前项目已实现目标确认、动作消费、预算、无进展检测与检查点；没有通用独立Verifier，也没有累计token、费用或任务deadline硬门。completed仅表示本次模型正常结束。

## 模块四 · 第2题：Session busy时，新消息或异步工具完成事件到达怎么办？

先区分消息语义，再修改状态。目标设计采用持久事件队列与会话单写入者：外部计算可以异步，Session共享状态按明确顺序更新。事件携带session、逻辑任务、run、目标版本和操作身份；不能只按“哪个Session正在运行”投递。

本项目默认Queue：普通消息等待当前整项任务完成，不混入正在执行的模型上下文；暂停时继续保留队列。用户显式Steer才影响当前任务，改变目标或写入范围时重新确认；Stop在调用边界阻止后续操作，保留已经产生的结果。

异步结果先持久化并去重，再核对归属及目标版本。匹配当前任务则作为工具结果供下一次决策使用；迟到或失效结果留档，不能驱动新目标，也不能与另一轮工具请求错误配对。需要通知时记录独立的会话事件；结果到达不等于用户已经看到。

取消不等于副作用撤销。工具可能已经完成写入但响应丢失，此时状态应是unknown，按操作回执或外部查询核对，再决定恢复；不能因为换了call ID就重复执行。状态串行、持久CAS和业务幂等分别解决进程内顺序、持久版本冲突和重复副作用，三者不能互相替代。

取舍：默认排队降低并发度，但归属和恢复更清楚；同会话并行主任务需要进一步隔离可变状态与结果合并，目前不开放。项目研究子循环是受父任务控制的同步调用，尚未实现通用异步工具完成事件总线；提醒事件不能冒充这项能力已完成。

## 模块五 · 第1题：Claude Code与GLM／豆包的工具输出方式有什么不同，各有什么优缺点？

先分清产品界面、模型API和Runtime。Claude Code是应用，OpenAI-compatible function calling是接口约定；不能把可见界面等同产品全部内部实现。以下比较公开的Anthropic Messages客户端工具协议与GLM／豆包Chat Completions接口，不推断Claude Code未公开的内部细节。

| 对比点 | Anthropic Messages | GLM／豆包Chat Completions |
| --- | --- | --- |
| 模型请求工具 | assistant content内的tool_use块，input为对象 | assistant.tool_calls，function.arguments为JSON字符串 |
| 回传工具结果 | user消息内的tool_result，通过tool_use_id配对 | role=tool消息，通过tool_call_id配对 |
| 内容组织 | 消息按类型化内容块组合 | 文本与调用字段分别表示，其他类型依具体接口核对 |
| 执行错误 | tool_result支持is_error | 应用可在工具结果内容中约定结构化错误，依供应商扩展核对 |

两者均由模型提出调用请求，由客户端Runtime校验参数、检查权限、执行工具并回传结果。Anthropic的user角色在这里承载工具结果，不代表用户又发送了一条自然语言指令。两边都要维护调用与结果的配对，不能跳过失败的工具而留下不完整历史。

我的工程判断：内容块更适合表达类型与顺序，但解析、流式处理、归档和多模态适配更复杂；常见兼容接口便于复用SDK和服务生态，但JSON字符串仍需安全解析和Schema校验，“兼容”也不保证结束原因、推理字段和并行工具行为一致。不能据协议形式断言某家更快、更可靠。

项目选择轻量内部消息加双向Model Adapter，同时处理“厂商响应→内部对象”和“历史及工具结果→下次厂商请求”。保留必要原生字段，无法安全转换则拒绝；模型call ID负责协议配对，确认动作实例负责授权次数。切换模型只迁移可解释的历史、任务状态和证据，不直接转发另一家专用状态或盲重试未知写入。

MCP属于工具发现和调用层，不能替代模型消息Adapter。当前项目实际接入DeepSeek／OpenAI Responses；本题的Chat Completions比较不能直接套用到Responses，也不代表已实现Anthropic、GLM或豆包适配。

依据（核对于2026-10-21）：[Anthropic §Handling results from client tools／Handling errors with is_error](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)、[GLM §响应参数说明／代码示例](https://docs.bigmodel.cn/cn/guide/capabilities/function-calling)、[豆包Chat API §messages.tool_calls／messages.tool_call_id／choices.message.tool_calls](https://docs.volcengine.com/docs/ark/chat-api?lang=zh)。以上优缺点为工程评价，没有虚构性能对比。
