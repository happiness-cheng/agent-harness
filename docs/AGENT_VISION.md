# 我想构建什么样的 Agent

这个项目起点是一道“从零实现最小 Agent”的笔试。我想借这个机会，把自己使用 Agent 时反复遇到的问题，变成能够解释、实现和验证的设计：它需要先理解我想做什么，给出合适的能力，在明确的边界内执行，并让我知道结果是否可信。

本文的“我”指项目作者。内容依据两份已公开的讨论整理；引文标注用户消息编号，AI 参与追问、实现和文档整理。目标设计、当前实现及参考资料分别说明。

## 我的起点：一个公式，四个部分

**Agent = LLM + 工具 + 上下文 + Harness**

我把 Harness 单独列出来，是为了强调模型之外的工程责任：信息怎样进入模型，行动怎样获得授权，状态怎样保存，失败怎样处理，结果怎样验证。这是工程分工的表达；Harness 在实现上也管理工具和上下文，四项不是互不相交的数学集合。

最初，我将单个 Agent 分成四个部分：

| 部分 | 我希望它回答的问题 | 当前范围 |
| --- | --- | --- |
| ① 决策与上下文 | 模型应该知道什么？需要怎样决策？ | 系统提示、需求对齐、Plan / Build、按需提供上下文 |
| ② 知识与能力 | 模型如何完成任务，如何与外部交互？ | 工具描述与 Schema、待办与提醒、公开资料研究、渐进披露 Skill |
| ③ 执行与运行时 | 如何安全执行任务？出错怎么办？ | Session、权限、调用循环、预算、恢复、错误反馈与 trace |
| ④ 评估与进化 | 如何验证修复、发现缺陷、持续改进？ | 已有工程测试和验收；自动评估与持续进化作为后续方向 |

这是职责划分，不是四个必须按顺序执行的服务。决策、工具与执行形成循环，评估根据实际证据检查循环的结果。最小版本优先完成前三部分；多 Agent 协作和第四部分的完整运行机制后续再展开。

来源：[需求共创 · 用户005](ai-conversations/01-design.md)。

## ① 决策与上下文：我首先在意它有没有理解我

> 模型决定上限，但如果意图理解错误走错方向那就越走越远

这是我作为重度 Agent 用户最在意的问题。很多请求最初只是模糊想法，模型如果过早执行，可能高效地完成了一个与我期待不同的结果。

我倾向于先说明理解，完成需求对齐再执行；同时不增加一个独立的意图分类模型，也不要求每个简单问题都重新走一遍规划。用户可以主动进入 Plan / Build；已有目标清楚时继续推进，目标或写入范围改变时再对齐。只读工具可以帮助理解需求，但“只读”也需要权限判断，读取私人信息同样可能有风险。

系统提示词需要交代身份、目标、决策方式、工具使用、不确定性、失败及完成判断。它可以借助模板起步，内容则要根据实际工具能力和失败案例修改。

我还区分两件容易混在一起的事：**给模型什么信息**与**信息变多后怎样处理**。前者是必要上下文与渐进式披露，后者是预算、归档和压缩。

来源：[需求共创 · 用户007、010、013、015、053](ai-conversations/01-design.md)。

### 必要上下文按需提供，历史尽量追加

我的初始构想是：系统提示词、工具定义、Skill 摘要以及适用的 Memory 构成必要信息；用户输入、模型回答和工具结果逐步追加。信息应该在需要时出现，不能因为“可能有用”就全部常驻。

为了维护缓存一致性，大工具结果先保存原文，再生成被冻结的模型预览，补读作为新结果追加。压缩也只调整工作视图，不能把会话上下文当作业务状态的唯一存储。

讨论中，我进一步明确了压缩的取舍：

- 同一份材料在不同任务下应保留不同内容。摘要要结合目标、用户要求与证据需求。
- 先分块提取再让模型摘要时，如果提取阶段已经漏掉关键信息，后面的模型无法凭空恢复。分块覆盖能力同样需要验证。
- 对冲突应查原因，不应在摘要时自行选一方；保留原文、引用和当前状态，恢复时核对。
- 先做便宜的处理，最后才用模型完整压缩，并为反复失败设置熔断。80% 等阈值是讨论策略，不能保证预测后续消耗。

其中两句原话是：

> 摘要不是简单的总结概括内容，而是结合任务目标，用户要求做上下文感知压缩

> 保留冲突，去查清楚为什么

来源：[需求共创 · 用户057](ai-conversations/01-design.md)；[架构推演 · 用户014、018、020、022、024、045](ai-conversations/02-architecture.md)。

当前已实现冻结工具预览、会话归档与分层压缩，但动态应用状态仍放在早期位置；不能据此声称整个请求前缀已经稳定或缓存命中率已验证。服务端上下文编辑也只是按提供商能力评估的方案，不是当前通用功能。

### Memory 应服务当前任务

我在讨论中选择全局、项目和会话三个作用域，并继续追问：模型怎么知道存在可用的记忆？哪些内容值得提前保存？分类之后，冲突和召回是否真的解决了？

我的判断是看当前价值、长期价值、复用可能和时效性；当前明确要求不能被历史偏好覆盖。用户应能决定哪些信息可以保存、哪些不应记录。评价也要同时看召回覆盖、无关记忆、使用效果和用户体验。出现问题时，分清是检索、上下文组装还是模型使用出了问题，再控制变量排查。

来源：[架构推演 · 用户049、051、054、060、062、064、066](ai-conversations/02-architecture.md)。当前只实现 Session 内记忆，跨会话长期记忆留待后续。

## ② 知识与能力：工具要让模型知道“什么时候用”

我讨论工具时，首先关注的是描述的质量，而不是工具数量。描述需要说明使用时机、边界、不接受的输入、返回值和示例；Schema 约束参数，描述帮助模型选择。

“搜索相关内容”只说明能做什么；“当需要获取实时信息或查找未知事实时使用”才开始说明何时该用。工具多了以后，还需要考虑如何分组、按需暴露，避免选择混乱和上下文膨胀。

我将能力分为三个方向：感知工具获取外部信息并处理信息体积；执行工具产生实际动作，需要输入校验和权限约束；协作工具负责委派与整合，后续再扩展。描述不能承担全部安全责任，真正的执行边界必须由 Runtime 检查。

来源：[需求共创 · 用户018](ai-conversations/01-design.md)。当前没有开放通用 Shell，也不会将讨论中的命令黑名单视为完整的安全隔离方案。

### 从一句“记得提醒我”推敲能力边界

我提出过这个测试场景：

> 我明天要写一份周报，你记得提醒我

它没有显式说“调用 todo”，却表达了需要记录和提醒的意图。工具描述应该覆盖这种自然表达；但识别出意图，并不代表已经知道提醒时刻，也不代表已经获得所有执行权限。

由此进一步确定：待办按 Session 隔离，支持删除；截止日期与提醒时刻分开；到点提醒用户，暂不自动执行任务；通知同时考虑会话内和操作系统桌面。桌面显示与点击尚未验收，不能把 API 接受等同用户已经看到。

来源：[需求共创 · 用户025、027、030、033、035](ai-conversations/01-design.md)。

### 公开研究由子循环搜索，再按问题保留证据

我先追问“何时打开网页、正文太长怎么办”，随后又追问“系统怎么知道该搜索哪些内容、需要哪个网址”。因此选择让研究子 Agent 自主搜索、阅读、补查，并针对研究意图组织结果，而不是预先用程序猜好所有 URL。

这个选择允许主循环只接收必要的证据和结论，代价是额外的模型调用、预算和验证。研究结果需要来源、原文位置、限制和未查明项；不能把搜索摘要当作已读证据。

来源：[需求共创 · 用户041、043、045](ai-conversations/01-design.md)。当前研究子循环共享父任务预算和 trace，实际网页读取与结果预览仍有确定性截断，不能说任意长材料已经实现了完整无损的语义压缩。

## ③ 执行与运行时：错误必须能处理，也必须能解释

我补充过三类错误反馈：系统能安全处理的错误、需要把明确错误交还模型的情况，以及需要用户决定的高风险情况。

例如参数要求整数、模型给出字符串“123”，系统即使允许规范化，也应反馈发生了什么转换，而不是静默猜测用户意图。不能安全转换就返回校验错误；失败后是否可重试，要看真实执行状态。当前并未实现通用自动类型纠正，不能把这个讨论例子当成既有能力。

来源：[需求共创 · 用户021](ai-conversations/01-design.md)。

### 循环有边界，但复杂任务应该有继续的方式

固定10轮可能做不完，放得太开又可能陷入死循环。这是我提出软阈值的原因：接近资源边界时先提醒并整理成果，达到硬门则保留状态、报告未完成部分，再由用户决定是否继续。

无进展不能只看调用次数，还要看相同调用和状态是否变化。预算恢复不能清空原消耗；模型正常结束也不等于业务目标已经通过验证。

来源：[需求共创 · 用户060](ai-conversations/01-design.md)。当前按调用次数设置硬门，并预留一次无工具收尾；累计 Token、费用和整个任务时间门尚未实现。

### 新消息、迟到结果和 Memory 更新都需要看归属

我希望默认让当前整项任务完成后再处理普通新消息；只有用户明确停止或引导时才改变当前执行。共享状态串行更新，计算是否并行是另一项选择。

在后续推演中，我关心稳定幂等键、旧版本识别以及变化是否影响当前任务。用户的语言偏好发生变化，不应让一个已明确要求 C++ 的任务自行切换到 Python。取消等待也不代表外部副作用已经撤销；结果未知时要查真实状态。

来源：[需求共创 · 用户053](ai-conversations/01-design.md)；[架构推演 · 用户080、088、094、096](ai-conversations/02-architecture.md)。当前默认 Queue，显式 Steer / Stop；尚未开放同 Session 并行主任务或通用异步工具事件总线。

### 日志是下一阶段的优先项

当前有模型、工具、运行和研究子循环 trace，但详细诊断仍不足：模型错误会被概括成统一错误码，外层异常和进程崩溃也可能丢失尚未落盘的 trace。

下一阶段先补具体错误原因、关联 ID、受控输入输出引用和及时落盘，再做调用树及标准观测接口。日志应能帮助判断问题出在哪一步，不能为了详细而保存密钥、所有私人内容或隐藏推理。此段是本次日志讨论形成的后续需求，尚未实现。

## ④ 评估与进化：先把模糊目标变成可验收条件

我最初就把“验证修复、发现缺陷、持续改进”列为第四部分。架构讨论时，我进一步提出：模糊任务如何转换成明确可验收内容？能否先用代码或明确规则检验？测试成功是否真的对应用户目标？

我的底线是检查验收证据，还要核验测试内容、测试版本及用户真实需求。计划可以调整，但调整应该有利于目标，同时考虑时间和资源。对比方案时控制变量，避免把多个变化混在一起后错误归因。

来源：[架构推演 · 用户026、035、070、074、076](ai-conversations/02-architecture.md)。

当前测试与验收为这部分提供基础，还没有自动评价、经验提炼、自我修改与回归发布的完整闭环。后续先让运行证据足够可靠，再讨论自动进化。
