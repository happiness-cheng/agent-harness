## 1．2026 年 10 月：从 Agent Harness 笔试出发

**问题与起因。** 作者希望借最小 Agent 笔试，实现一个理解意图、能使用工具、可控执行且能够核验结果的 Agent。仅有模型回答无法承担权限、状态与恢复责任。

**思路、选择与理由。** 用户005提出 `Agent = LLM + Tools + Context + Harness`，并划分四项职责：

1. 决策与上下文：模型应该知道什么，怎样理解意图并决策。
2. 知识与能力：怎样通过工具、Skill、Memory 与外部交互。
3. 执行与运行时：怎样执行、管理状态、控制权限和处理失败。
4. 评估与进化：怎样验证结果、发现缺陷、纠错并持续改进。

共同讨论校准了一个边界：这是职责公式，不是四个彼此独立的服务；Harness 也组织工具和上下文。最小版本优先实现前三部分，基本测试不能推迟，第四部分的完整自动进化保留为长期方向。

| 当时的问题 | 共同形成的选择 | 为什么这样选 |
|---|---|---|
| 方向理解错，执行越多返工越多 | Plan / Build，范围改变时重新对齐 | 明确目标后才投入副作用操作；简单问题不重复规划 |
| 上下文越来越长，关键条件被淹没 | 按需提供、原文保留、冻结视图与分层压缩 | 保留可回查依据，避免把所有信息常驻或摘要当事实 |
| 模型不知道工具何时适用，参数也可能错误 | 明确描述、Schema、返回值、错误反馈 | 工具选择与执行校验各自承担责任 |
| “只读”“Build”被误当成全面授权 | 按访问资源和动作检查权限，区分风险 | 读取也可能涉及隐私，模型不能自行扩大权限 |
| 任务中断或结果未知 | Checkpoint、预算、恢复前核对持久状态 | 恢复不等于重置预算，未知副作用不能盲重试 |
| 模型说完成但没有实际证据 | Trace、真实工具结果、独立验收 | 声明与事实分开，失败必须可定位 |

**行动与结果。** 仓库已形成 Python Runtime、工具、会话持久化、检查点和评测相关模块；实现由作者确定目标与取舍，AI 协助解释、实现和验证。源码及历史验收入口见 [AGENT_VISION](AGENT_VISION.md) 与 [PROJECT_STATUS](PROJECT_STATUS.md)。

**目标与假设。** 这些机制不证明任意自然语言任务都能正确完成，也不证明完整自动进化。后来的局部评测与受限改进不能倒写成初期已经实现。

## 2．从最小 Agent 转向个人智能系统

**问题与起因。** 按本次用户的演变说明，最小 Runtime 成形后，单次执行无法覆盖长期项目：会话结束，目标、阻塞和维护义务仍在。

**思路、选择与理由。** 从“完成当前请求”扩展到理解长期目标、跟踪项目和未完成事项、维护成果、发现问题并提出改进。会话提供交互上下文，项目与目标要有持续的状态，才能减少反复解释。

**行动与结果。** 目标范围被明确扩展；既有 Memory、任务和验证工作提供部分基础，但不能据此声称完整个人智能系统已完成。

**目标与假设。** 长期理解是否准确、主动建议是否有价值、成果维护是否可靠，仍需真实使用验证。

## 3．AI 资源规划引出私人管家

**问题与起因。** 用户提供的历史说明指出，后续长期讨论从 ChatGPT、Codex、DSH、Qoder、免费模型额度与学生云资源的管理需求开始。资源分散，额度、成本与使用安排依赖人工协调。

**思路、选择与理由。** 最初思路是管理 AI 资源；进一步发现资源规划只是更大问题的一部分：用户还要协调信息、任务和长期目标。因此将需求扩展为私人管家，而不是只维护一张额度表。

**行动与结果。** 本次归档保留这条需求因果链；当前未取得该轮讨论或资源调度验收记录，不宣称自动管理账号、额度或云资源已实现。

**目标与假设。** 统一协调能否真正降低成本与管理负担仍待验证；提到平台不代表已接入其接口或获准读取账号。

## 4．第二大脑和私人幕僚

**问题与起因。** 单纯执行和资源管理无法覆盖共同思考、跨项目关联以及成果的长期维护。

**思路、选择与理由。** 长期定位为理解用户长期目标、关联个人信息、共同思考、主动发现问题、把想法变成成果并持续维护的个人智能系统。这个定位强调持续价值，不以聊天数量或 Agent 数量衡量能力。

**行动与结果。** 按本次用户说明归档产品方向及边界：不是单纯聊天机器人，不是大量 Agent 的机械集合，不是自动收集所有对话的数据库，也不能擅自替用户作出所有重要决定。

**目标与假设。** “理解”“关联”“主动”仍是需要评价的能力目标；本轮归档不是这些能力的实现证明。

## 5．主 Agent 与专业 Agent

**问题与起因。** 长期领域需要连续积累，但各领域又共同服务于用户的总体目标。

**思路、选择与理由。** 主 Agent 负责全局目标、路由、跨项目关联和优先级；专业 Agent 按学习、项目、资源等长期领域分工。用户可联系主 Agent，也可直接与专业 Agent 交互，避免所有交互必须绕行一个入口。

**行动与结果。** 设计上区分四个概念：会话是交互入口，任务是一次要完成的工作，项目组织相关成果与工作，长期目标指导跨阶段取舍。会话不是项目状态的唯一存储。本次保存该设计，未据此创建多 Agent 系统。

**目标与假设。** 领域分工不等于已有可靠路由、跨 Agent 一致性或共享权限；专业 Agent 也不自动获得更多数据访问权。

## 6．主动性与权限演进

**问题与起因。** 私人管家需要主动发现问题，但错误判断若直接触发行动，会扩大风险。

**思路、选择与理由。** 采用“主动发现问题 → 提出建议 → 获得授权后执行 → 验证可靠后有限自主”的渐进路线。能力提升不能自动转换成权限提升，有限自主也需要明确范围。

**行动与结果。** 将这个路线作为长期设计约束保留；与早期 Runtime 的“模型提出、程序校验”一致。本轮未启用后台自主行为。

**目标与假设。** 在哪些任务上足够可靠、如何撤回授权、什么情况下停止，需要各阶段真实证据；不能用平均得分抵消权限底线。

## 7．选择两个真实应用试点

**问题与起因。** 个人智能系统范围过大，继续扩展抽象设计无法证明真实价值。

**思路、选择与理由。** 首先选择学习与思考、个人项目与目标：前者关注真正理解而非只输出答案；后者关注进度、阻塞、关联工作和长期任务维护。这两类场景能够直接检验是否减少用户负担。

**行动与结果。** 本次按用户说明记录试点选择；不虚构试用完成率、学习提升或项目效率收益。

**目标与假设。** 价值要通过真实使用效果检验。会回答问题或保存待办，都不足以单独证明试点成功。

## 8．为什么需要跨平台 Activity Connector

**问题与起因。** 用户的学习和工作发生在 ChatGPT、Codex、DSH、Obsidian 等平台，而非只在 Adrian 中。如果每次都人工复制记录，系统没有减少管理成本。

**思路、选择与理由。** 通过获授权的 Connector 采集活动，首先考虑 Codex 和 DSH，再扩展其他平台。区分“原始活动 → 可信事件 → 活动理解 → 长期记忆 → 授权行动”，避免采集结果直接变成记忆事实或行动许可。

**行动与结果。** 确定 Connector 方向与优先顺序；本轮不读取源平台私人历史，也不安装 Hook 或插件。

**目标与假设。** 接口可用性、数据覆盖与授权范围需要分别验证；“采集得到”不等于“理解正确”，更不等于“允许行动”。

## 9．Phase 0 至 Phase 0.1.2.4.2：身份与观察分离

**问题与起因。** 按用户提供的历史说明，调查涉及历史文件格式、Codex 多 rollout 与 Fork 身份，以及 DSH old/v4、seq/seq0、修订与工具事件关联。仅用序号或正文哈希去重不足以区分身份与观察。

**思路、选择与理由。** 序号可能依赖格式与局部上下文；相同内容也可能是不同发生位置或不同来源的事件。保留这些不确定性，比静默合并更可靠。选择三层职责：

| 层 | 要承担的职责 | 要避免的混淆 |
|---|---|---|
| Identity Manifest | 保存身份依据及不可变 Snapshot Root，校验 revision 关联 | 普通追加或进度更新不应改变身份 |
| Observation Store | 保存 Snapshot / Observation，定位最新观察 | latest 变化不覆盖最初 root |
| Checkpoint Store | 保存处理位点 | 运行进度不充当身份来源 |

**行动与结果。** 用户指定调查与设计已形成 `Unified Event Model v0.2.4.2-final + Errata 2` 基线，并要求确定性 ID、幂等、崩溃恢复和不确定性保留。本仓库尚未找到这些阶段原记录及冻结正文，因此上述内容只归档已提供的设计摘要，不作为调查重现或实现一致性证明。

**失败与纠正的证据边界。** 可以解释为什么不能简单用序号/内容去重；目前不能声称某个具体 DSH 或 Codex 样本已复现何种碰撞，也不能编造历次 Errata 修正内容。取得原阶段材料后再追加准确来源，保留历史原文。

**目标与假设。** 确定性身份的具体命名空间、规范化输入、revision 哈希规则、StateEvent 冲突语义和恢复边界必须从冻结正文核对，不能仅凭术语自行填补。

## 10．进入 Phase 0B：让实验决定下一步

**问题与起因。** 前期讨论已形成用户指定的设计基线，继续无限修订文档不能证明设计可运行。

**思路、选择与理由。** 先 M1 三层存储与重建一致性，后 M2、M3，再根据实际结果推进 Connector。优先复用 Python 与本地 SQLite，不为实验引入新服务；存储方案仍须在取得冻结正文后核对。

**行动与结果。** 本轮已核对工作区、建立 `adrian/phase0b-m1` 工作分支并归档演变。M1 因冻结正文缺失尚未编码；这不是实验失败，也不是需要修改架构的证据。具体执行状态见 [本轮记录](phase-records/2026-11-05-phase0b-entry.md)。

**已确定的验收。** 仅使用合成数据：A 身份稳定且普通追加不增 Manifest revision；B root 不变、latest 更新；C StateEvent 可 fold，非法冲突报错；D 保留必要持久状态后重建，确定性 ID 一致；E revision、哈希、父 revision 损坏时失败且拒绝继续写入。展示重建前后 ID 和损坏错误，保留失败证据。

**目标与假设。** 尚未运行 A–E，不能宣布 M1 完成或进入 M2。完整 Connector、Fork、实时 Hook、自动 Memory 集成、真实私人数据与模型效果均不在本轮实施范围。

## 2026-11-05 追加：从历史反例到 M1 实现

**材料补齐。** 用户提供 Phase 0、0.1、0.1.2、v0.2.4.2 和 Final Errata 五份报告，随后明确选择 Final Errata 为当前基线。两个设计报告原文存入仓库；早期调查提取因果摘要，未复制私人 thread 标识和设备活动细节。旧报告中的原执行结果是历史证据，不是本轮重新调查所得。

**历史纠正。** Codex 单文件 ordinal 连续不能证明跨片段唯一；后续报告发现不同事件的序号碰撞，并区分续写片段与真正 Fork。DSH 仅按 seq 续读会漏掉 seq0；old/v4 各有不同事件层，不能只取 v4。额外 tool/result 中有修订，数量配平仍不能证明唯一调用关联。throughSeq 从可能的本地持久化水印被纠正为下游确认。这些问题解释了为什么要分离身份、观察、位点和不确定关联。

**设计落地。** Final Errata 进一步把可变 head 改为不可变 root，把 status 移出身份注册，将 root_evidence 移出 ID，并要求 manifest_id/hash/parent 同时校验。本轮采用独立 SQLite 三层表、追加链、状态 fold 和位点 CAS，避免在生产 Runtime 上试验新存储模型。

**真实失败与修复。** 新增损坏测试发现 JSON 重复键被静默覆盖、布尔值冒充 revision；已添加严格解析和类型检查。独立演示首次因 Windows SQLite 句柄未关闭而清理失败，修复关闭连接后重跑成功。这些是实现缺陷，没有据此扩大或重写冻结架构。

**结果与边界。** 本轮 A–E 合成演示通过，重建前后 10 个身份 ID 一致；新增 31 项测试与原检查点相关 32 项回归合计 63 项通过。仅证明本轮受限 profile 的存储机制，不证明完整 Connector、业务事件崩溃恢复或真实模型理解。M2 可作为下一批开始，本轮不执行。
