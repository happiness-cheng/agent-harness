# 工程记录制度 · 工程日志

- 建立：2026-11-04（v1）；同日按 AEF-001 升级为 v2；同日按 AEF-002 审核意见校准为 **v3**
- 强制约定入口：[AGENTS.md](../../AGENTS.md)「工程记录制度」节（随会话加载，效力最高）
- 冲突处理：`AGENTS.md` 与本文件不一致时以 `AGENTS.md` 为准；差异在对应日志末尾追加更正说明，不静默改写任一侧
- 版本说明：v2 **取代** v1「每个编码任务一份独立 Markdown」的组织方式，理由与 Trade-off 见 [DECISION_LOG](DECISION_LOG.md) 的 AEF-001；v3 仅校准适用范围、职责边界与条件必填，不改变三类日志与 Task ID 关联机制，理由见 AEF-002。v1／v2 已产生的历史日志保留原样，不迁移、不改写
- 目录边界：本目录只放工程日志与制度文档；`docs/phase-records/` 的阶段调查报告保持独立，不覆盖、不删除、不迁移

## 1. 核心原则与适用范围

每一次落入适用范围的任务都必须留下完整、可追溯的记录。记录的不仅是「改了什么」，更要保留：为什么做、依据是什么、为什么选当前设计、考虑过哪些替代方案及 Trade-off、做了哪些验证、最终结果。**禁止只记录修改结果而不记录设计理由。**

**完整日志制度适用于**：

1. 实际编码任务
2. 工程规则变更
3. 架构设计变更
4. 数据模型变更
5. 权限边界变更
6. 会影响工程行为的配置变更

**不强制建立完整三类日志**：纯阅读、纯调查、只读分析、普通内容性文档修改、不改变工程规则的文字修正。这些任务仍应遵循对应阶段的调查报告要求。**纯调查若转为实际编码，应在开始编码前建立记录**（不是事后补建）。

## 2. 三类日志职责与 Task ID

| 日志 | 只记录 | 不记录 |
|---|---|---|
| [DECISION_LOG.md](DECISION_LOG.md) | 重要架构决策、设计理由、替代方案、Trade-off | 实施过程、改动清单、测试明细 |
| [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md) | 任务目标、实施过程、实际修改文件、实施偏差、未完成事项、副作用 | 设计权衡论证、测试命令与结果、失败证据、风险、验证结论 |
| [VALIDATION_LOG.md](VALIDATION_LOG.md) | 测试命令、环境、测试结果、失败证据、风险、验证结论 | 实施步骤、设计理由、改动清单 |

规则：

- 每个适用任务一个**唯一 Task ID**（建议 `<项目前缀>-<序号>`，如 `AEF-002`），同时写日期与 Phase；三册通过 Task ID 互相关联。
- **同一事实只在其归属的日志写一次**，避免重复记录：IMPLEMENTATION_LOG 引用 VALIDATION_LOG 的 Task ID 与对应条目即可，**不重复抄录测试明细**；反之 VALIDATION_LOG 不重述实施步骤。
- 重要决策必须能追溯到对应实现与验证；追溯靠 Task ID + 条目引用，不靠复制内容。
- 三册均为**追加式**：历史条目不得删除或改写；更正以追加说明方式写入。
- 单册过长时按 Phase／周期分卷，分卷不改写旧内容。

### 条件必填（避免强制记录过度）

| 日志 | 何时必填 |
|---|---|
| IMPLEMENTATION_LOG | **每个适用任务必填** |
| VALIDATION_LOG | **每个适用任务必填** |
| DECISION_LOG | **仅当发生重要设计决策、架构选择、规则变更或 Trade-off 时必填** |

- 工程规则变更属于「规则变更」，**必须**在 DECISION_LOG 记录（AEF-001、AEF-002 均属此类）。
- **没有新决策时不强制创建空记录或写入无意义的占位内容**；此时在 IMPLEMENTATION_LOG 注明「本任务无新决策」，并指向已有决策条目即可。
- 判定口径：改动是否引入新的工程行为约束或架构取舍。仅修错别字、调格式、普通内容性文档修改不触发 DECISION_LOG。

## 3. 执行前（动手改文件之前，必须建立记录）

复制 [TEMPLATE.md](TEMPLATE.md) 中「执行前」段到 IMPLEMENTATION_LOG，填完再动手：

1. Task ID
2. 任务目标与范围
3. 当前项目基线及工作区状态（Git HEAD、`git status --short`、已有未提交改动归属）
4. 预期修改的模块
5. 设计依据与相关决策
6. 已知风险和禁止操作

## 4. 执行过程中（必须记录）

1. 实际完成了什么
2. 为什么需要进行这些修改
3. 修改了哪些文件及其具体作用
4. 关键设计选择及其原因
5. 考虑过哪些替代方案，为什么没有选择
6. 是否发现与原有设计不一致的地方

设计决策写入 DECISION_LOG（**有条件必填，见第 2 节**），实施细节写入 IMPLEMENTATION_LOG；发现的不一致要如实记录，不因结论不利而省略。

**去重规则**：第 ④⑤ 项（关键设计选择、替代方案与 Trade-off）只在 DECISION_LOG 写一次；IMPLEMENTATION_LOG 写「见 DECISION_LOG → `<Task ID>`」即可，**不重复抄录**。若本任务无新决策（DECISION_LOG 未创建条目），在 IMPLEMENTATION_LOG 注明「本任务无新决策」并指向已有决策条目。

## 5. 执行结束后（必须补齐，按职责分册写入，不重复）

1. 实际修改文件清单
2. 测试命令、环境和测试结果
3. 新增／通过／失败／跳过的测试数量
4. 失败原因及处理情况
5. 尚未解决的问题（**必须明确写出哪些工作没有完成**）
6. 潜在风险及影响范围
7. 是否产生数据库、文件、配置或其他副作用

分册归属：②③④⑥ 与失败证据、验证结论 → VALIDATION_LOG；①⑤⑦ 与实施偏差 → IMPLEMENTATION_LOG。IMPLEMENTATION_LOG 只写「见 VALIDATION_LOG → `<Task ID>`」，不抄命令与数字。

测试口径：区分通过／失败／跳过／未执行；**没有实际执行的测试不得标记为通过**，未运行的一律标 NOT RUN；测试通过不等于功能正确，程序测试通过不能证明自然语言效果，必要时写明验证范围。不得把未经验证的假设记为事实。

## 6. 完成门禁

适用任务结束前必须：① 检查实际 Git Diff ② 核对修改文件清单 ③ 执行与修改范围相关的测试（按风险选范围，已有可信全量证据可注明来源复用，不机械重复整套）④ 记录准确结果（含失败／跳过／NOT RUN）⑤ 更新**适用**日志中本 Task ID 的条目（IMPLEMENTATION_LOG、VALIDATION_LOG 必填；DECISION_LOG 按第 2 节条件）⑥ 向用户总结做了什么、为什么做、验证结果、未完成工作与遗留问题。

**日志未完成，本次任务不得标记为完整交付。** 未完成任务标 PARTIAL / BLOCKED，不得伪装成完成。

## 7. 约束与授权边界

- 不为记录而泄露私人对话、凭据、Token 或其他敏感信息。
- 不修改历史记录来掩盖失败；更正一律追加说明。
- 不将未经验证的假设记录为事实。
- 每次任务必须明确记录哪些工作没有完成。
- 不自动扩大原任务范围；记录制度不构成额外修改授权。
- 任何任务仍须遵循用户明确指定的只读、修改范围、审批和数据安全边界；未经授权不删除原始数据、不执行 Git commit / push。
- 记录尽量模板化、自动化，不成为繁琐负担。

## 8. 记录制度示例（真实片段，来自 AEF-001）

以下为 AEF-001 的真实记录，展示三册如何以同一 Task ID 关联、各自只写一类事实：

- **DECISION_LOG → AEF-001**：「三类日志用追加式分册取代 v1 每任务独立文件」+ 原因 + 替代方案 + Trade-off + 发现的 4 处设计不一致；末尾交叉引用另两册。
- **IMPLEMENTATION_LOG → AEF-001**：执行前 6 项基线（HEAD `50b27bf`、` M AGENTS.md`、`?? docs/engineering-log/`）→ 执行中实际改动文件及作用 → 执行后未完成工作与副作用。
- **VALIDATION_LOG → AEF-001**：实际执行的检查命令、环境、通过／失败／跳过／NOT RUN 数量、失败归因、自检报告、范围确认。

三处不重复：设计权衡只在第一册，改动清单只在第二册，命令与数字只在第三册。完整内容见各册 AEF-001 段。

> 注：AEF-001 产生于 v2 规则下，当时 DECISION_LOG 为无条件必填；v3 起按第 2 节条件必填执行。历史条目按约束保留原文，不回溯改写。

## 操作细则

- **判定先于记录**：先按第 1 节判断是否适用；不适用则不建完整三类日志，纯调查转编码时在动手前补建。
- **编码前**：在 IMPLEMENTATION_LOG 追加本 Task ID 的执行前段，填完 6 项再动手。
- **编码中**：**有新决策时**才在 DECISION_LOG 追加同 Task ID 段；实施进展追加到 IMPLEMENTATION_LOG；方案调整与发现的问题如实记录，不回头改写已写内容。无新决策不写占位。
- **编码结束**：按 `git diff` 与 `git status --short` 填实际修改；命令、环境、数量、失败归因、风险与验证结论追加到 VALIDATION_LOG；IMPLEMENTATION_LOG 只引用 Task ID；更新索引状态；逐项核对第 6 节门禁。
- **更正**：写 `[YYYY-MM-DD] 更正内容：原因与依据`，追加到对应条目末尾，不改历史正文。
