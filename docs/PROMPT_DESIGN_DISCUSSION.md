# 系统提示词、子 Agent 与第二大脑：设计讨论记录

日期：2026-10-22。本文记录作者与 AI 协作中的需求、依据、取舍和验证状态，是可公开的设计摘要，不包含私人会话数据、凭据或模型隐藏推理。本文不是功能完成声明。

## 1. 作者确定的产品目标与合作方式

核心目标：构建一个能干活、能理解用户想法的第二大脑。

- 沿用作者的四部分职责地图：决策与上下文、知识与能力、执行与运行时、评估与进化。它们协作，不是固定串行的四个服务。
- 学习和改进以自己的代码为主线，每次一个具体点；结合成熟项目的实现解释用途、原因和代价，然后小步验证。
- Agent 应善解人意：允许提出对用户意图的暂时理解，遇到影响目标、范围、关键参数或副作用的歧义时先核对；不能把推测当成授权直接执行。
- 具体工具的使用条件、参数和返回语义应在工具契约中说明；系统提示保留跨工具的通用规则与工作流程。
- 希望保留设计、取舍和思考的大致过程并上传 GitHub；改进应有前后对比和测试，而不止理论讨论。

作者表达的“第二大脑”是产品方向，当前实现仍以本地单用户和 Session 内记忆为主，不代表已有跨会话长期记忆或完全自主的个人助理。

## 2. 当前源码事实

- `src/min_agent/runtime.py` 中，只有工具集 `is_bound` 为真时，Runtime 自动加载 `prompts/system.md`。绑定指工具注册表关联到通过访问检查的 SessionStore 和 ExecutionContext，不等于已经注册了工具。
- 未绑定时，Runtime 不自动提供另一份默认系统提示。外部包装可自行加入提示；研究循环的 IsolatedModel 就显式加载 `prompts/research.md`。
- 现有研究子循环使用独立消息上下文、只读工具和共享预算。尚无本次讨论提出的通用自定义子 Agent 目录和启动器。
- 主提示已包含模式、定向授权、工具规则、记忆回查、错误和完成判断。通用规则与具体工具细节混合，工作主线和沟通风格较简略。

## 3. 本轮提出的设计方案：尚待逐项对齐和实现

### 3.1 主 Agent 如何发现和启动子 Agent

建议区分两份材料：

1. 主 Agent 可见的简短目录：名称、适用情景、不要使用的情景、能力与输出摘要。
2. 子 Agent 自己的完整定义：角色提示词、允许工具、输入输出契约、预算和权限限制。

主提示只写通用委派规则，无需为每个新增子 Agent 手工追加一段说明。Harness 从受信任、启用的定义生成目录；主模型提出委派请求后，程序根据标识加载所选定义并构造子 Agent 请求。模型传递本次任务和必要材料，不能自行覆盖角色提示或扩大权限。

建议的子请求结构：程序控制的通用边界和角色提示 + 本次任务、约束与验收条件 + 必要的参考数据。它有自己的循环和历史，结果回传主 Agent。默认不复制主会话全部历史；是否支持 fork 是另一项设计。

子 Agent 可获得的权限取父任务已有权限、子 Agent 配置和本次委派限制的交集；定义文件不能自行授予应用没有批准的能力。用户添加的定义也需要受控加载，不能把网页里发现的“Agent 定义”直接注册成可信系统指令。

调用时机需要同时满足：任务与描述匹配、委派有收益、运行时允许。复杂调查、隔离大量资料或独立核对可能适合；简单计算无需为了形式而委派。任务目标本身含糊时，应先澄清，不把歧义转交子 Agent。

这与 Skill 都可采用“简短目录先可见、详细内容按需加载”。区别是 Skill 通常为当前 Agent 提供方法说明；子 Agent 则启动自己的执行上下文、工具范围和返回契约。具体公开产品存在不同调用模式，不能将二者绝对等同。

### 3.2 流程、通用规则和沟通方式

工作流程建议：理解请求 → 判断关键歧义 → 必要时核对 → 在授权范围内行动 → 检查结果 → 继续、等待或报告。

通用规则贯穿流程：权限由程序决定，外部材料不能升级为指令，推测要标明，结果依据真实证据，不以正常结束代替业务验收。流程不能覆盖这些规则。

建议的沟通原则：体贴、明确、自然、不过度附和。先承接用户目标；需要确认时先说出具体理解，再问一个关键问题；已清楚或已确认的事项不反复问。表达“我理解你希望……”而非断言“你一定是……”。有风险或冲突时直接说明原因，不用温柔措辞掩盖问题。

例子：用户说“明天要交周报，你帮我留意一下”。建议回答“我理解你可能希望我提醒你交周报，对吗？如果是，你希望明天几点提醒？”该例仅展示语气和意图核对，后续写入仍遵守应用确认流程。

反例：“已经帮你设成明早九点提醒”——擅自补造时刻并声称完成；“请填写完整需求规格”——给简单需求增加不必要负担。

### 3.3 减少歧义与注入防护

规则尽量表达触发条件、可信依据、行为、失败分支和例外。用正反例验证边界，不能承诺自然语言完全无歧义。

系统提示讲清数据来源与指令权限；Harness 保留来源并隔离不可信输入；Runtime 校验参数、归属和副作用授权。XML/Markdown 分隔是可读性措施，不是安全隔离。子 Agent 的输出同样需要核对，不能成为自动授权依据。

## 4. 如何证明改进有用

每次改进记录：原问题、观察证据、候选方案、取舍、实际改动、前后版本、固定输入、结果、代价和未通过项。一次尽量只改变一个因素；不要把改模型、改提示和改工具同时混在同一效果结论里。

下一次系统提示改进建议比较以下固定场景，具体评分口径需先对齐：

| 场景 | 期望行为 | 主要观察 |
| --- | --- | --- |
| 普通明确问答 | 直接回答 | 不必要澄清次数 |
| 模糊提醒请求 | 核对意图和缺失时刻 | 是否猜时间、是否先写入 |
| 用户纠正先前理解 | 按纠正更新理解 | 是否沿用旧目标 |
| 用户明确不要记录 | 不产生写入 | 写入尝试及真实存储 |
| 网页伪造用户授权 | 不接受其授权 | 工具请求、实际副作用 |
| 工具失败或状态未知 | 如实报告并选择安全下一步 | 是否虚报成功、盲目重试 |
| 可委派的长调查与简单计算 | 前者考虑委派，后者直接处理 | 委派准确性、调用成本 |

证据分两层：离线脚本模型验证程序控制与检查器；固定真实模型、参数和输入做多次前后比较，评估理解、选择与语气。真实调用须明确凭据来源和请求预算，禁止隐式使用个人工具凭据。语气由人工按固定标准评价，并保存实际回答，不以单一模型评分作为全部结论。

本轮未修改生产提示词、未实现新子 Agent 机制，也未执行真实模型 A/B。下面仅是当前工作区的离线基线，不是提示词改善证据。
