# v0.6 B2预算阻断根因

## 可复核证据

基线 `30f6126`，历史原始材料为 `reports/memory_v06/prepared-client-fix.json.gz` 与 `live-client-fix.json/.jsonl`。每题前两次公开 Message 经过真实 Runtime 重放，并逐字比较已保存请求；第三次是**离线反事实请求**，没有送往 API。

输出 `v06-budget-breakdown.json` 按15题、每次请求记录系统、历史工具消息、工具 Schema、动态 Memory/授权状态、原生状态、输出预留、单次与累计上界以及门禁。组件可能重叠，不能把各列相加当成总字节。历史日志没有第三轮完整原生状态，因此有些字段明确是下界或未知，而非精确计量。

## 已证实的原因

- 原 Capture 与 MeteredModel 各有上下文预检，都把每次最大预留永久累加；完成请求后的真实 usage 没有返还未使用的预留。
- 原式：`len(encoded(Message列表)) + len(encoded(raw_tools)) + 8192`；单次32768，累计65536。与模型调用3次和工具4次的独立限制分开。
- 15题第三轮的**累计计数下界**均已超过65536，范围66959～77835。因此累计门禁本身足以独立阻断全部15题。不能由此排除单次门禁也同时成立。
- 银行题前两次预留44352，第三次旧计数下界29344，累计下界73696。第三次原生状态不完整，不能伪造精确历史数值。
- 每次请求仅1个 system、1个动态投影，没有旧投影累积；未发现单次重复拼接系统提示或工具索引。稳定提示/Schema在每次API请求中再次提供不属于此类错误。
- Message 的逻辑工具调用与 provider_state 是内部双表示。现有 Provider 将校验后的原生表示发出，内部计数却把两者都算入。DeepSeek 原生状态是 reasoning content，不应误称为 OpenAI encrypted reasoning。

## 修复及门禁保留

使用实际协议JSON而非内部对象计量，已完成请求按真实usage结算，下一轮完整预留。单次32768、累计65536、输出4096、3轮模型/4工具不提高；未知usage立即关闭。详细语义见根目录 `MEMORY_ACTIVE_RETRIEVAL_V07.md`。

`p0-control.json` 保存同一个合成Provider的旧/新闭环：旧 partial/context_limit，新 completed/3模型/2工具，第三轮确实包含证据。usage为人为设定，不是账单或模型效果成绩。

单次过大、累计Token过大、模型次数、工具次数、全局调用、usage未知/越界仍有独立测试。`test_active_trial_v07.py` 进一步令第二次响应产生过大原生状态，第三次被单次门禁拦下，整批只执行首题B0/B2，后续题没有发起请求。

## 未知与不能声称的内容

v0.6 未保留第三轮原生状态，无法精确复原当时单次请求。Mock只证明记账与控制流；真实模型可能因更多原生状态、更多工具轮次、证据选择或推理错误而失败。真实运行结果单独报告，不将未发出的准备材料当作已送达证据。
